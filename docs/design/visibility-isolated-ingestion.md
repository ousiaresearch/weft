# Visibility-isolated ingestion and legacy migration

Status: proposed architecture, not implemented. Baseline is the working tree, including uncommitted changes; line references are navigation aids, not a released-version claim. Do not enable this design until the gates below pass. The initial release is fresh-only; all descriptions and tests of candidate reuse, deduplicated retries, and earliest-eligible selection below apply only to a future optional mode blocked by the selection gate. In particular, fresh-only retries allocate new bundles, not the prior ID.

## Problem and current evidence

* `weft/ingest.py:156-216` derives document Source IDs from scope and raw content hash and paragraph IDs from the Source ID; media does the same at `:218-300`. Thus identical bytes and scope collide regardless of who can see the resulting records. The document job lookup happens before incumbent bundle validation; media reads a job directly and then checks its Source. A scope alone is not a visibility partition.
* `weft/scope.py:213-244,261-339` contains mutable scope/marker configuration, content-sensitive decisions, and write checks covering payload, provenance, source IDs and record type. Read checks take the engine's flattened record text. Marker or context changes can change access without changing the scope. Provenance and paragraph content can distinguish access within a bundle. Neither a scope key nor a frozen visibility label proves present access.
* `weft/substrate.py:112-165,344-384,448-480` has `records`, FTS5, jobs unique on `(scope, source_id, stage, content_hash)`, receipts, journal and meta. `PRAGMA user_version` is currently 4; older jobs are dropped during the v4 migration. `job_state` checks scope against empty text, not the source or bundle. `set_job` authorizes a stub. This is not a safe public deduplication oracle.
* `weft/substrate.py:278-299,428-444,487-607,750-860` provides a SQLite ingestion transaction, record/FTS writes and per-scope/model sqlite-vec tables; inspect actual extension behavior before promising atomic vector DDL/DML. Projections are external files (`:1048-1189`) and are not transactionally committed with SQLite. Journal visibility is currently scope-gated (`:1025-1045`), not necessarily record-content-gated. Existing journal IDs and details must be reviewed for exposure.

## Security contract and limits

An incoming ingestion must never reuse, reveal an ID for, mutate, or derive public job state from an incumbent unless the authenticated caller has **both read and write authority on every member of the completed bundle**, including Source and all Observations, at the applicable linearization point, and the incumbent matches the request under the hash-bounded contract below. Validate the proposed physical bundle too. Existence, mismatch, unreadability, missing members, and inaccessible job metadata are not externally distinguishable as conflict details. An unauthorized candidate is skipped internally; ingest a fresh isolated bundle if the request itself is authorized. Return only the caller's own authorized resulting ID or a generic refusal/failure, not candidate counts or reasons.

This prevents deterministic-ID collision and explicit candidate/job-state disclosures; it does **not** promise constant time, eliminate resource/load side channels, hide raw-content equality from privileged database operators, or protect data already exposed in historical IDs, logs, projections or backups. Names and metadata remain subject to the same authorization as content. Restricted database access and operational isolation are prerequisites. Rate limits and timing defenses need separate analysis.

## Proposed identity and schema

Use opaque independently allocated IDs in reserved fresh namespaces `doc-v5-<token>`, `media-v5-<token>`, and `obs-v5-<token>`, with 128-bit lowercase hex tokens produced by the collision-free allocation gate below. Source and observations are independently allocated; no ID, including a paragraph ID, encodes content, scope, ordering or another ID. Legacy IDs remain untouched and usable through existing authorization. For new records, raw content hashes are sensitive internal candidate keys, not public identifiers or record provenance. Current provenance can expose a content hash; remove it from new public records and all public projections, logs and APIs. Legacy provenance and previously disclosed hashes remain exposed wherever existing authorized reads or copies contain them; migration does not retroactively erase them. Audit those surfaces and restrict or explicitly accept the legacy exposure before rollout, without silently rewriting historical evidence.

Reserve the entire `doc-`, `media-`, and `obs-` prefixes using ASCII case-insensitive matching, including legacy deterministic Source and paragraph forms, for trusted ingestion allocation. All generic creation, overwrite and correction-replacement entry points must refuse such caller-selected IDs with the same public result before any existence lookup, independent of whether an incumbent exists or is readable; internal ingestion must use a non-forgeable trusted path, not a caller-controlled flag. Audit alternate write interfaces and normalization for bypasses. Authorized reading and deletion of legacy records remain possible subject to the deletion gate below; corrections to a legacy original may use an independently allocated nonreserved replacement under normal authorization. This closes that chosen-ID oracle only in the ingestion-ID namespace, not in the global caller-selected ID namespace, nor past disclosures or timing channels. Nonreserved globally unique IDs can still disclose existence or be squatted across scopes; a separate all-record ID allocation/keying redesign is required to close that residual.

The trust boundary is a narrow authenticated service API: untrusted clients cannot execute Python in the service process, invoke private library methods, access `_conn`, supply executable plugins, or access the database, sidecars or service credentials. Same-process code with those capabilities is trusted and can bypass these rules; this design does not sandbox it. Deployment must enforce and test the boundary, not rely on Python naming conventions or a boolean flag.

After migration to a new explicitly assigned schema version (provisionally 5; confirm no intervening version), add the following fresh-only SQLite tables in the same database, plus the structural descriptor and allocator state specified below; their exact DDL and constraints are implementation and review gates. They are internal only, inaccessible through generic job/read APIs. Reuse-specific columns, indexes and evidence are not created or populated for the initial release; their future schema requires a separately reviewed migration and retention policy. `records` and existing foreign links remain unchanged. All TEXT encodings are UTF-8; hash BLOBs are raw 32-byte SHA-256. A future candidate index, if approved, must be nonunique.

```sql
CREATE TABLE ingest_bundles (
  source_id TEXT PRIMARY KEY REFERENCES records(record_id) ON DELETE CASCADE,
  kind TEXT NOT NULL CHECK(kind IN ('document','media')),
  scope TEXT NOT NULL,
  member_count INTEGER NOT NULL CHECK(member_count >= 1),
  created_at REAL NOT NULL
);
CREATE TABLE ingest_members (
  source_id TEXT NOT NULL REFERENCES ingest_bundles(source_id) ON DELETE CASCADE,
  ordinal INTEGER NOT NULL CHECK(ordinal >= 0),
  record_id TEXT NOT NULL UNIQUE REFERENCES records(record_id) ON DELETE CASCADE,
  PRIMARY KEY(source_id, ordinal)
);
```

Ordinal 0 is the Source, higher ordinals are ordered observations; media has only ordinal 0. These tables are fresh-only structural/completion evidence used for immediate post-insert validation and authorized bundle inspection, not a lookup or reuse index. A successful fresh commit does not consult an incumbent. No completion sequence or reuse-ordering counter exists in the initial schema; the independent ID allocator requires its own separately specified state. Enforce in application and migration validation: source record is Source, source_id equals ordinal 0 record_id, member count and contiguous ordinals agree, scopes match, observations have exact expected Source links and no extra members. Foreign keys do not enforce these cross-row constraints. Deletion, correction, overwrite, repair and cascades must scrub bundle metadata as specified below; `ON DELETE CASCADE` alone can leave an incomplete bundle and is not sufficient. Incomplete/stale metadata is never success and cannot be repaired using an inaccessible incumbent.

Intact authenticated bundle membership is defined exclusively by the validated membership table, not by reverse `source_ids` or `supersedes` links. After scrub no surviving record is presented as a complete authenticated bundle. Nonmember records may cite or supersede members, but are not bundle output and must never be presented by retrieval, expansion, projections or downstream consumers as authenticated bundle content. Ordinary graph traversal must authorize each record independently. Gate reuse on auditing and testing every consumer of these relationships; disable the affected reuse/expansion path if this distinction cannot be enforced. Reverse links still matter for deletion safety below.

For any member deletion, overwrite, correction or other semantic mutation, atomically delete the entire bundle metadata and membership set before or with that mutation; do not merely mark it invalid. This scrubs the live membership metadata and, in a future reuse mode, request fields, hashes, manifest and related reuse/vector evidence, without deleting unrelated surviving records. Rollback restores both; subsequent reuse requires a newly completed bundle. Check all mutation paths, cascades and SQLite `INSERT OR REPLACE` behavior, including triggers and foreign-key settings. This is logical deletion from the live database, not a promise of physical erasure from WAL, freed pages, backups or external copies; retention and secure disposal require separate operational policy. Minimize manifest copies: store structural descriptors and cryptographic digests where possible, and compare exact canonical output using live authorized records against freshly derived document output; a digest alone is not exact comparison. For media, exact comparison of stored output with a protected canonical manifest requires retained canonical fields; if that retention cannot meet deletion/confidentiality policy, disable media reuse rather than weaken verification. Never retain raw input solely for reuse.

All permitted database writers must use a verified connection configuration with foreign keys enabled; reject unsafe connections and prohibit direct operator writes outside a separately reviewed maintenance procedure. Database triggers independent of foreign-key cascading must additionally scrub metadata on relevant member mutation; explicitly handle or prohibit `REPLACE` and verify recursive-trigger settings and every permitted SQL form. Triggers are defense in depth, not a claim that arbitrary privileged SQL, disabled triggers or unsafe connections are contained. Test pragma-off connections and `REPLACE`; Records triggers cover DELETE and UPDATE of a member, INSERT of any record superseding a member, and explicitly tested REPLACE effects; an insert trigger must invalidate the superseded bundle even though the original row is unchanged. Vector-only changes require a separate trusted vector-write wrapper that transactionally scrubs affected bundle metadata, with reuse-time evidence checks as an independent backstop; vec0 virtual tables do not provide equivalent row triggers. If every permitted writer cannot be constrained to these paths, block activation.

In any future reuse mode persist only allow-listed nonsecret settings required for identity; resolve credentials separately from a secret store. Tokens, passwords, URL userinfo, secret query parameters and sensitive headers must not enter canonical requests, manifests, journals, logs, projections or errors. If a secret affects output, bind an opaque versioned credential/config identity that is safe to store, not the secret or its guessable hash; unknown or unclassifiable settings disable reuse. Apply redaction before persistence and test nested settings and failure paths.

For future reuse only, fingerprint v1 uses SHA-256 of a precisely versioned, canonical UTF-8 JSON encoding: sorted keys, compact separators, no NaN, with explicit type tags and all fields required by the ingestion contract. Request includes kind, scope, byte hash, document name, author, parser/fence/paragraph algorithm versions, attribution, media kind, adapter identity and settings, and required embedding model/configuration; never include caller identity as a substitute for authorization. Store the canonical request fields in protected internal metadata, not merely their fingerprint, and compare those fields after lookup. Raw input is not retained solely for deduplication: raw byte equality is **SHA-256-bounded**, not exact. A collision of distinct raw inputs can cause reuse if every other check passes; collision resistance is an explicit assumption, not a proven guarantee. Canonical output fields and actual member structure are compared exactly, not just by output hash. Output covers ordered intended records' type, scope, payload, attribution, epistemic status, effective time, supersedes, provenance and normalized internal Source links, excluding physical IDs and creation time; define a deterministic representation for links and vector requirements. Exact parser/model version availability is a gate: if not reproducibly identifiable, don't reuse that candidate. Unknown versions fail closed.

Media retry semantics are **earliest committed currently eligible result wins**, not fresh inference equivalence: after processor authorization, look up and authorize an eligible complete stored output before invoking the adapter; a hit returns that output without rerunning inference. A future separately reviewed reuse migration must add its own completion sequence and counter; no such fields exist initially. Allocate a durable, unique completion sequence within the serialized commit transaction, ordered by commit serialization, and select the lowest sequence among currently eligible matches; using `ingest_completion_counter`: initialize its sole row to zero at migration/new-store creation; under the same `BEGIN IMMEDIATE`, increment it and assign the new value to the bundle before commit. Rollback rolls back both. Never derive it from wall time or rowid; reject allocation at signed 64-bit maximum rather than wrap. Deleting or scrubbing a bundle never decrements/recycles the counter; the next eligible remaining sequence wins. Offline restore must validate counter >= every surviving sequence and restore a consistent database; since post-backup writes are lost, this ordering describes surviving history only, not discarded bundles. No merging independently restored lineages without a separately reviewed resequencing protocol. Eligibility changes can change the selected result. A miss runs the adapter and publishes a new output; concurrent preparations may differ, and the transaction recheck may select an already completed eligible result. Explicit fresh/non-reuse mode bypasses candidate lookup and selection both before inference and during the final transaction, even if an eligible incumbent exists or commits concurrently. It must run inference and publish its own newly authorized bundle or fail; an allocation invariant violation fences the store rather than causing a retry. A successfully published fresh result is eligible for later ordinary reuse, but does not displace an earlier currently eligible result. Verify stored output against its manifest and actual records; never claim it equals a hypothetical new inference. This does not eliminate hash-collision risk.

Fresh-only media provenance must also obtain processor identity from a server-owned trusted registry binding the actual trusted execution to its immutable identity; if not verifiable, label the identity explicitly unverified and prohibit downstream consumers from treating it as authenticated model provenance. Processor permission is still mandatory. Media reuse requires a server-owned trusted processor registry binding the selected implementation and immutable artifact or provider deployment identity/version to all output-affecting configuration, plus a trusted execution path and protected evidence binding that execution to the resulting bundle. Resolve identity from the registry, never from a callable's self-reported attribute or caller-supplied digest. Disallow caller-supplied executable adapters on this path. For remote providers, require a verifiable immutable deployment identity and a documented trust/attestation basis; otherwise disable reuse. A manifest proves self-consistency, not inference provenance or output correctness; registry evidence depends on the trusted execution/provider boundary and is not proof that the model is truthful. Unregistered or unverifiable processors cannot create reusable media bundles; disable media reuse entirely until this gate passes.

Vector reuse requires an internal collision-safe registry mapping a stable model identity to immutable artifact digest, preprocessing/settings, dimensions and actual physical vector table; table-name hashes alone do not establish identity. For future vector reuse, persist protected evidence binding each vector's bytes, member ID and canonical embedding input to that exact artifact/configuration and dimension, recorded atomically with the vector; fresh-only stores no reuse-only evidence or copied embedding input. Verify registry, ownership, expected member set and evidence against actual rows at reuse; tampering by privileged database operators is outside this trust boundary. Evidence establishes recorded provenance, not mathematical correctness: release requires an independently tested trusted generation path and either deterministic recomputation comparison or a documented model-specific bounded validation criterion. Missing, ambiguous or unverifiable evidence blocks vector reuse; rebuild only under authorized operator policy. Registry/evidence schema and validation thresholds remain implementation gates, not existing features.

Initial fresh-only ingestion writes no durable job row, including no completed or failed job; pre-completion progress is request-local memory only. Existing `jobs` cannot be made safe simply by adding a scope filter. If diagnostic jobs are introduced in a separately reviewed future mode, replace its caller-facing use with internal per-physical-bundle job state; do not expose running/failed candidate states before complete-bundle authorization. For that future schema, retain its columns and unique key for physical IDs, but remove scope-only `job_state` access and direct SQL lookup; gate all job reads and mutations through bundle authorization. New work before a completed bundle exists is private to the request, not keyed by a predictable source ID and not externally queryable. For a public progress endpoint, use an unguessable request capability bound to its authenticated owner, revocation and expiry, and do not include candidate state. This capability and ownership mechanism are additional implementation gates, not assumed current features.

For a new ingest, successful transactional publication and validation of its bundle row, complete membership, records and required vectors establish completion for that operation and later authorized structural inspection; the initial mode does not consult this metadata for retries or candidate selection. A row alone is insufficient if integrity checks fail. Jobs, if retained, are diagnostic only, never a deduplication/completion predicate; stale, failed or absent jobs cannot override validated completion or create it. No API may surface diagnostic state without its separate authorization. Legacy job states never establish completion.

## Authorization and execution protocol

1. Authenticate the caller and resolve current grants from the authoritative boundary, not from caller-constructed `ScopeContext`. Before parsing, media processing, adapter or embedder invocation, authorize access to the actual input and the specific processor, destination, external transfer and temporary storage under the trusted input classification specified below; unknown classification or permissions deny. Enforce approved destinations, least-privilege temporary-file access and cleanup on failure/crash, and prohibit external transfer absent explicit grant. This input/processor authorization is distinct from subsequent output authorization and cannot be inferred from an empty stub. Parse/fence documents after this check; media lookup precedes inference as described above. Do not reject an otherwise eligible incumbent based on hypothetical newly allocated IDs: actual physical record authorization occurs on each incumbent or, on a miss, on the actual proposed bundle in step 3. Revalidate authority before each external side effect if it may have changed. No job lookup is observable before authorization.
2. Except in explicit fresh/non-reuse mode, calculate v1 request fingerprint and retrieve internal candidates using the nonunique index; no caller-facing candidates, counts, diagnostics, or jobs. Under the synchronization contract below, load each candidate and its complete manifest. Reject malformed, unsupported, incomplete or changed candidates internally. Independently of metadata scrubbing, reject any bundle whose member has any superseding record, including corrections/retractions, or whose actual member fields differ from the manifest; perform this reverse-link check and member comparison under the final serialization, including vector-less operation. For every actual member, check `authorize_read(member.scope, ctx, engine._payload_text(member))` and `authorize_write(member, ctx)`; then compare canonical request fields, output, membership, links and vector requirements subject to the raw-hash bound. For media, compare stored output to its manifest, not a newly generated output. Never return a partial match. Do not use a privileged read result in an error, audit or response visible to the caller. If multiple fully eligible matches exist, choose the earliest committed completion sequence without reporting multiplicity.
3. If none qualifies, or mode is fresh/non-reuse, allocate independent IDs and materialize the new bundle. Require both current read and write authorization on every final physical record, including its allocated ID and actual Source links; normalized fingerprints do not substitute for physical-record policy checks. Apply both checks inside the final serialized transaction before publication, including every rebuilt link; an actual collision is a store-fencing invariant failure, not a recovery retry. The allocation gate below makes hidden-occupancy-dependent retries invalid; do not publish a replacement whose policy outcome depends on hidden occupancy. Embeddings are computed only after input/processor authorization and before publication where feasible; adapter/embedding failure is never a success. Revalidate proposed physical records and, for reuse mode only, candidates inside the final serialized transaction. Concurrent same-visible reuse requests may both prepare; only one publishes after rechecking, or both publish distinct isolated bundles if neither is mutually authorized. Fresh requests publish separately. There is no global uniqueness on content.
4. Acquire and fence the per-operation external authority lock first; then start `BEGIN IMMEDIATE` on the authoritative connection, verify the policy snapshot as specified below, and reread applicable records and required vectors (and candidates only in future reuse mode); either select a validated completed incumbent (never in fresh/non-reuse mode) or insert records, FTS entries, all required vectors, bundle and member metadata, appropriate journal entries, but no durable ingestion job row in fresh-only, then bump store version and commit. All successful paths require the specified validation, including retries and recovery; raw bytes remain hash-bounded. A rollback leaves none of the new authoritative bundle visible. If sqlite-vec cannot prove participation in the same transaction for the deployed version, block vector-enabled rollout or use a separately designed durable pending/rebuild protocol; do not claim atomic completion.
5. After commit reauthorize and release the Source ID under the response fence below; if authority was revoked, do not disclose the ID even though the commit remains. Projection regeneration is separate and must not turn an uncommitted ingestion into success. The projection access and revocation gate below applies to every projected view. A projection failure after SQLite commit means committed data with projection pending, not a failed atomic database transaction; if the ID cannot be disclosed under the response fence, give only a generic outcome. An authorized operator may retry projection regeneration independently; it is not an ingestion retry. If commit outcome is ambiguous (connection lost), return unknown, never success. In fresh-only there is no request-to-bundle binding or candidate lookup: a new ingestion retry allocates and may commit a second bundle, not revalidate the first. The first may remain committed but undisclosed and can appear in independently authorized search/recall; it is not automatically orphaned, hidden or reaped. Duplicates and their storage/consumer effects are accepted operational residuals; no safe automatic cleanup or idempotency is promised. A future owner-bound idempotency capability and its privacy, authorization and recovery protocol require separate review. Failed job/audit persistence cannot be described as durable; surface operational audit failure without exposing candidate details.

All client-visible refusal/error types, messages, status and response fields must be normalized across hidden-candidate versus no-candidate cases; actual request validation errors may remain meaningful only when independent of hidden state. Suppress sensitive candidate IDs/content in logs, tracebacks, metrics labels and denial journal details. Administrative diagnostics require separate explicit authority. Do not promise identical timing.

### Deletion and hidden dependents gate

Current scope-only deletion is not sufficient and must be unavailable to untrusted clients before activation. Under the same authoritative policy and write serialization, resolve the actual target and the complete effects of deletion, including database cascades, bundle metadata/evidence scrubbing, FTS/vector changes and all affected records and reverse references (`source_ids`, `supersedes`, and other discovered dependencies). Require current read and write authority on the actual target and every record changed or deleted, using its actual content and identity; no implicit authority follows from scope or ownership of the target. An unknown, malformed or unenumerable dependency graph fails closed. If any dependent is hidden or unauthorized, reject the entire operation without mutation; do not report which dependent or how many. Never silently delete, rewrite, orphan or cascade through hidden records. If a dependency would be left dangling, either authorize and apply its explicitly specified mutation as part of the same transaction or reject; do not infer permission to alter it. Verify dependency discovery against every actual schema and concurrent insertion under the same serialization.

For absent, unreadable, unwritable and blocked-by-hidden-dependent targets, expose the same generic non-success response, status and fields; no boolean distinguishing absent from present and no affected counts, IDs or details. An authorized successful deletion may report success, but only after the complete authorized transaction and response fence. Administrative diagnostics are separately authorized. Apply these rules to legacy and new IDs, all delete interfaces and cascades, and any overwrite, correction or repair with equivalent destructive effects. This is conservative: an otherwise authorized deletion can be unavailable until dependent records are resolved by an authorized operator. Timing and resource effects remain outside the indistinguishability claim.

## Policy concurrency: required new authority boundary

The present `ScopeEngine` holds mutable in-memory sets/maps; the SQLite transaction and a per-Substrate process lock do not freeze policy or synchronize other processes. Merely rechecking immediately before commit has a TOCTOU gap. The selected model is an immutable authoritative policy/grant snapshot and durable monotonically increasing epoch in SQLite. Authenticate principal through a trusted boundary; derive grants and all policy inputs from that snapshot, never trust caller-supplied grants, actor or `user_authored`. Every policy mutation, grant change and revocation must use the same database write serialization; prohibit direct mutable engine changes and out-of-band authority updates. Under `BEGIN IMMEDIATE`, read the snapshot/epoch, authorize all actual records, perform writes, and commit while authority changes are excluded. Define and test lock ordering for every store and policy path. An epoch alone without those enforced preconditions is insufficient.

**Rollback-resistant authority gate:** the SQLite epoch alone is not monotonic across restore, stale replica promotion or replacement. Use the concrete external serialized authority protocol below, outside the database and its backup/restore domain. Every policy mutation, write and disclosure must participate; matching counters or checking once on startup is insufficient. No leases or bounded-staleness exception are selected.

On every open, restore, failover or promotion, fence service access first, compare lineage and watermark, and reconcile all policy changes since the snapshot, including revocations, against the authoritative history before allowing reads, writes, external processing or handoff. Separately satisfy the deletion recovery gate below; policy replay alone cannot establish data freshness. Reject stale, ahead, divergent, unprovable or ambiguous state until an explicitly authorized reconciliation establishes a current snapshot and new fenced lineage; matching counters alone do not prove matching history. Never restore authority from an old backup as current authority. Test restore after acknowledged revoke, equal-counter divergent histories, failover, crash between each external/SQLite step, stale replicas and concurrent response handoffs. Authority outage blocks security-sensitive operation; this design does not claim this distributed protocol is already implemented or that a watermark alone solves atomicity.

Bound input bytes and per-bundle member count independently of hidden candidates. The selected initial rollout disables reuse for every request, so it performs no candidate scan and always creates an independently authorized bundle; no scan-limit result can distinguish hidden from absent candidates. Earliest-eligible retry semantics are therefore NOT offered in that rollout. Enabling the optional reuse protocol requires the selection gate below; do not silently enable it or claim both bounded scan work and complete earliest-eligible selection. Bound normal transaction and external-authority waits with deadlines, roll back on failure, and measure revocation latency under admitted load. Operational failures and contention can still affect availability and are not a noninterference guarantee.

For disclosure, reserve bounded capacity in a trusted, server-owned outbound handoff before acquiring authority serialization. Under that serialization re-resolve the authenticated principal, reauthorize the entire resulting bundle, and atomically commit an immutable response containing the ID to that reserved handoff; this nonblocking, bounded operation is the disclosure linearization point. Release the fence immediately afterwards, before any socket, network I/O, streaming, client-controlled backpressure or waiting for queue space. If capacity cannot be reserved, reject or retry generically without an ID; if enqueue fails, release the reservation and disclose nothing. The handoff must be an actual irrevocable commitment for delivery by the trusted server, not merely a mutable response object subsequently rechecked or selectively sent; revocation ordered after enqueue cannot retract queued or in-transit bytes. Bound queue size, reservation lifetime and lock hold time, and fail closed on timeout. Remote identity revocation that cannot participate in this ordering blocks this security-sensitive rollout; no bounded-staleness exception is selected. External processor transfers already performed cannot be recalled. Test policy change during derivation and at every boundary, including a stalled client and saturated queue while unrelated writers progress. Until these mechanisms exist, isolation remains a design goal.

## Legacy migration and rollout

Preserve all existing record IDs, references, journal history and vector keys. No global ID rewrite, aliases, or normalization; deterministic legacy IDs remain guessable and cannot be made opaque retroactively. Do not promise old external links or leaked identifiers become private. The new opaque allocator rule applies only to newly created records. Select **zero legacy candidate backfill for all kinds**: retain legacy records as readable under authorization, but never promote them into trusted reuse metadata based on writer-supplied hashes, jobs, provenance or deterministic IDs. In particular, media's first-completed rule cannot authenticate legacy inference provenance. Document re-derivation and exact output comparison may reduce risk but do not alone prove every request, version, vector and authority binding; any future backfill needs a separately reviewed design and authorization.

**Offline preflight, with all Weft readers/writers and policy changes stopped:** take a verified SQLite-consistent backup including WAL state using a tested backup procedure, and protect/backup projections and external artifacts separately. Inventory `sqlite_master` including triggers, indices, virtual and shadow tables, `PRAGMA user_version`, `meta`, column definitions and FK state; list every known version and exact expected DDL. Compare a permitted schema manifest, not just the version integer. Unknown versions, unexpected triggers/tables/columns, malformed JSON, inconsistent references, missing extension support or ambiguous derivation block migration and require operator review; never drop unknown objects. Account for SQLite FTS5 shadow tables and sqlite-vec shadow tables rather than treating them as arbitrary extras. Check existing startup `executescript(_SCHEMA)` and migrations do not mutate an unknown database before validation; migration entry must preflight before any schema-changing initialization.

Audit records and `source_ids`/`supersedes`, jobs and their statuses/reasons, journal IDs/details and authorized exposure, FTS rows against payload and scope, all vector virtual tables/models/dimensions/keys and orphans, receipts, projections/manifests/files, backups and external references. Journal is historical evidence: do not rewrite or delete it silently. Before any untrusted access or new-ingestion activation, scope-only journal access must be disabled or replaced by a policy that cannot reveal hidden bundle IDs, existence, counts, timestamps or details, including deleted/missing records and historical entries; suppress entire unsafe entries, not merely IDs. A privileged-only journal is acceptable until a separately reviewed record-aware design exists. Isolate stale projection files until a verified rebuild under the correct view; do not delete unmanaged files without explicit authority. Determine model identities from actual available metadata; hashed table names alone are not reversible. If identities or row ownership cannot be established, block reuse/rollout or explicitly invalidate and rebuild under operator-approved policy, preserving a recoverable backup.

**Explicit migration entry:** ordinary constructors, startup, CLI and library opens must inspect an existing store without mutation, using a read-only, no-create open and no journal-mode, schema, chmod or other modifying initialization before validation; refuse missing, older, unknown or forward stores. Account for SQLite WAL/sidecar read-only requirements and fail closed if a safe inspection is impossible. They must never implicitly run this migration. Only an explicitly invoked, operator-authorized offline migration command may proceed after verified backup, preflight, exclusive ownership and the external fence; command name and interface are implementation deliverables, not an existing command. The command fails closed on missing proof and rechecks ownership/fencing at mutation. New-store creation is a separate explicit safe path. An in-database old-writer tripwire may be added as defense in depth only after compatibility testing; it cannot fence old readers, direct SQLite, or privileged bypass and never replaces the external fence.

**One SQLite transaction:** after validating and acquiring exclusive operational ownership, `BEGIN IMMEDIATE`; revalidate schema and input inventory, create the proposed fresh-only tables with zero legacy candidate backfill and no candidate index, quarantine or drop/rebuild jobs only under an explicit migration rule after inventory and recovery assessment (never infer `done` from a scope-only job), verify counts, referential integrity, membership invariants and FTS/vector consistency. Historical startup uses `INSERT OR IGNORE` for `meta.schema_version` while migrations advance `user_version`, so equality is not a valid historical assumption. Discover and enumerate supported `(user_version, meta.schema_version)` pairs and exact associated schemas from actual creation/migration paths and fixtures; unknown pairs or manifests block. Normalize both version markers to the new version in this transaction only after validation. Failure at any point rolls back schema, data and version together. Verify this with the actual SQLite/extension and initialization path; virtual table or extension behavior is a release gate. A migration cannot atomically change files outside SQLite. Keep projections offline until separately rebuilt and validated; report them pending if rebuild fails. Validate `foreign_key_check`, `integrity_check`, expected schema, and reopen on a separate connection after commit.

**External binary fence is a precondition, not a schema-version feature.** Current old binaries can accept a newer version, so updating `user_version` does not stop them. Before migration, stop all old readers and writers; deploy an enforced service/OS access boundary that denies their identities access to the database, WAL/SHM, backups and containing directory while granting access only to verified new binaries. Inventory all access paths, scheduled jobs and credentials; disable old deployments and prevent restart or direct file access. Test the actual old binary with its real operational identity attempting open, read and write against a migrated fixture, including restart and direct SQLite access: each must be denied by the boundary. Exercise positive access by the new service and repeat after failover/restart. If shared credentials or ungoverned local access make that impossible, migration and rollout are blocked. A future forward-version check in new binaries is defense in depth, not a fence against already deployed old binaries. Privileged OS administrators able to bypass the fence remain outside the guarantee.

**Rollback:** the narrowly verified migration-backup exception in the recovery gate below permits restoring the exact fenced pre-migration backup before any post-backup mutation or deletion is accepted, after external authority reconciliation and all exception checks. Otherwise the general deletion recovery gate applies and restoration stays fenced. After any new writes, restoring backup loses them: stop service and use a forward fix; no automatic downgrade or silent restore. Reserved-ID cross-store import/export reconciliation is unsupported until separately designed, privileged, audited and reviewed; raw SQL is not an authorized workaround. Restore test includes WAL, projection handling and post-backup revocations. Maintain a migration report with sensitive values redacted and privileged detailed inventory separately.

## Round-three resolution: concrete boundaries and remaining gates

### Selection without a logical scan-limit oracle

The default release deliberately offers **fresh-only ingestion**, including media: no candidate lookup, no reuse, no promise that retries return an earlier ID, and no first-completed media retry behavior. The existing optional reuse protocol above describes a future gated mode, not an enabled capability. Reject any request for reuse with the same configuration-level unsupported response regardless of hidden state. Enforce the mode server-side, not by trusting a client flag. Test hidden versus absent at, below and above the former scan limit: both take the fresh path and produce authorized new IDs, subject only to request-independent infrastructure failures. Rate-limit by principal and input size, not hidden candidate counts.

Optional reuse may be enabled only after a separately reviewed, demonstrated selection mechanism preserves complete earliest-eligible selection without any hidden-candidate-dependent budget/deadline failure or truncation. A full unbounded scan can preserve selection semantics in an ideal completed execution, but cannot satisfy the bounded lock/revocation-latency and availability goals; timeouts and overload can themselves create a logical existence channel. Thus unbounded scan alone does not pass this gate. An authorization-indexed bounded scheme would need to prove completeness under content-sensitive mutable policy, policy updates, corruption, and concurrent inserts, without exposing hidden counts; no such scheme is specified here. Do not enable reuse by calling this an accepted leak. The no-reuse default is a functionality tradeoff, not a claim that a bounded solution has been found. Resource/timing channels and global infrastructure failures remain outside the contract even in fresh-only mode.

### Authority protocol and failure semantics

Deploy a linearizable, independently durable authority service with an authenticated per-store lineage, ordered policy log, epoch and snapshot digest, and a single exclusive **per-operation non-expiring lock** per store, acquired using an authenticated session and released after that operation. Each acquisition issues a strictly increasing fencing generation; it is not a process-lifetime ownership lock. On session loss or uncertain release the authority fences the old holder, and a replacement cannot begin until the old holder is demonstrably fenced from SQLite, processing handoffs and outbound handoff, not merely until a TCP disconnect or timeout. Every access boundary must reject stale generations, including an already-paused holder resuming after replacement; if this cannot be enforced for an already-open SQLite connection and every side effect, the store must remain fenced and activation is blocked. This fencing must be enforced by the storage/handoff access boundary; if it cannot be proven, deployment is blocked. A holder obtains the external lock **before** SQLite `BEGIN IMMEDIATE`; all writers, policy changes, processing authorization and disclosure handoffs use this same order. A revocation takes that lock, durably appends the new policy snapshot/digest and increments the external epoch, applies it to SQLite in a transaction, commits, and only then acknowledges; it keeps the lock until commit/ack decision. No other holder can write or enqueue while that revocation is in progress. If the external append succeeds but SQLite fails or its outcome is uncertain, keep the store fenced, do not acknowledge success, and replay the authoritative log idempotently into SQLite under a newly fenced holder before any operation resumes. An unacknowledged revocation may nevertheless have taken effect.

For a write or disclosure, while holding the per-operation external lock, fetch the authority's current lineage, epoch and snapshot digest, acquire SQLite serialization, compare the entire authenticated policy snapshot/digest and lineage, and authorize against that exact snapshot. Reconcile or fail closed on any mismatch. Hold the external lock through SQLite commit or the irrevocable outbound enqueue respectively, then release it. External processor transfers likewise require an irrevocable, bounded handoff ordered under the same lock after current authorization; no network I/O is performed under that lock, and queued or in-flight transfers cannot be recalled after revocation. If such a handoff cannot be enforced, deny external transfer. An authority RPC or lock acquisition has a deadline; authority outcome or release uncertainty aborts and fences the session rather than allowing operation on cached grants. A local work-deadline overrun with authority and lock ownership still known cancels work, rolls back any SQLite transaction, releases snapshot and lock normally, and returns a generic failure; fence only if cancellation, release or authority state becomes uncertain. If an RPC is needed while SQLite is locked its deadline counts against the transaction budget; timeout rolls back. The lock itself is not a lease and expiry is not permission to proceed. Recovery from holder crash or a partition may require operator or infrastructure fencing and can be unavailable indefinitely; a fencing system that cannot revoke a paused holder's access cannot implement this protocol. Slow or unavailable authority blocks all participating operations; this is an explicit availability cost and revocation latency is not guaranteed during partitions. Test crash at each append/commit/ack, session loss, paused holder resumption, split brain, stale lineage, and enqueue versus revocation.

### Read and disclosure serialization

The authority protocol applies to **all** untrusted content and metadata reads, not only ingestion responses: get, query, FTS, vector/hybrid recall, traversal/expansion, search counts, errors and every alternate API or library route. Reserve bounded handoff capacity before acquiring the per-operation authority lock. Under that lock acquire a consistent SQLite read snapshot, compare the authenticated current external lineage/epoch/digest with the full local snapshot, resolve the principal and authorize each actual returned record and any exposed derived fields against that snapshot. Construct an immutable complete bounded response, commit it irrevocably to the reserved trusted handoff while still holding the authority lock and with the data snapshot valid, then release the snapshot and lock before network I/O. Read-only transactions must participate in the same external serialization as deletes and writes; a SQLite read snapshot alone cannot order disclosure against them. Query filtering, pagination, counts, ordering and errors must not reveal hidden records. A cursor is not a continuing grant: each page is a new fenced request, with no promise of a stable cross-page snapshot. Streaming or responses that cannot fit bounded handoff are disabled until a separately reviewed chunk protocol exists; no unchecked stream or cached authorization is allowed. If capacity, snapshot comparison, authorization or enqueue fails, release resources and disclose nothing sensitive. Already enqueued bytes cannot be recalled; a revoke or delete acknowledged after enqueue does not retroactively retract them. Test all read routes with a paused stale process, revocation and deletion on either side of enqueue, queue saturation, and authority failure; no staleness window is selected.

### Deletion durability and recovery gate

An acknowledged delete must not resurrect live data after restore, failover or stale replica promotion. Policy epochs do not establish this. Before any such recovery serves reads, writes, processors or handoffs, retain the external fence and prove either (1) the restored database includes every deletion acknowledged before the fence, using a separately specified and independently durable authenticated data-history watermark tied to this exact database lineage and transaction history, or (2) an independently durable, complete deletion/effect ledger is replayed and verified. No such watermark or ledger is currently specified or assumed. Apart from the narrowly proved migration-backup exception below, until an independently reviewed protocol can prove one of these cases, recovery from any snapshot that might predate an acknowledged deletion is blocked, not silently allowed and not repaired by policy replay alone. Operator assertion, matching policy counters, an incomplete log, and inability to enumerate post-snapshot deletes are not proof. This gate also applies to rollback, break-glass erasure, and stale promotion, including before any projection or alternate reader is opened.

A future replay protocol must durably order deletion intent and its entire authorized effect set with SQLite commit and acknowledgment under the authority lock, reconcile every crash window idempotently before unfencing, cover record IDs and generations, dependencies, bundle metadata, FTS, vectors and projections, and prevent a later reused ID or independently created record from being deleted incorrectly. It must validate completeness against the independent watermark; an individual tombstone or timestamp alone is insufficient. Keep its sensitive identifiers, dependency information and audit evidence access-controlled and minimize retention under a separately approved policy. If complete effects cannot be recovered or legally replayed, remain fenced and escalate to an authorized operator; manual re-erasure is acceptable only if completeness is independently proven and the resulting store verified. This is live-store non-resurrection, not physical erasure of backups or external copies. Fault-inject before/after durable intent, SQLite commit and acknowledgment, restore pre-delete backups and promote stale replicas, then verify no deleted material is readable or present in derived indexes before unfencing; otherwise verify the fence remains closed.

### Processing, links, vectors and projections

* **Input classification:** bind a server-owned conservative label to the authenticated principal, configured ingestion channel and its permitted data sources before bytes enter processing. Client claims cannot lower it; absent or ambiguous binding denies processing. Authorization must explicitly permit this label for each processor, destination, temporary store and external transfer. This is an administrative upper-bound classification, not content inspection. Marker/content policy applies after extraction and cannot prevent a transfer already performed; channels lacking an adequately restrictive preclassification must use approved local processing or deny external transfer. Output policy can reject publication but cannot undo disclosure to a processor.
* **Link creation:** under the same authority and write serialization, generic creation, correction and replacement must resolve every `source_ids`, `supersedes` and other dependency target and require both read and write authority on each actual target, as well as on the new physical record. Missing, hidden and unauthorized targets have the same generic refusal; do not expose existence through errors or logs. Revalidate at commit against concurrent deletion/revocation. This intentionally restricts previously allowed links and requires a compatibility migration. Inventory all link semantics and delete effects, including supersession, Summary/Observation citations and verified-Claim reliance, and any discovered schema/plugin references; malformed or unenumerable references block the operation. Existing unauthorized links remain possible and are not silently rewritten.
* **Break-glass:** ordinary users cannot bypass hidden dependents. A separately authenticated privileged operator may initiate an audited, explicitly approved remediation, enumerate dependencies in a privileged environment, and either obtain authority for and atomically perform specified dependent changes or refuse erasure. Record approver, justification, affected identities, operations and result in protected durable audit before acknowledgment. If law/policy requires erasure but preserving hidden dependents prevents it, escalate; no automatic orphaning, unauthorized deletion, or guarantee of immediate erasure is claimed. Backups, WAL, external copies and privileged audit retention require their own retention policy.
* **Vector mutation:** gate all vector creation, replacement and removal, including direct `vector_put`, `_vec_remove`, corrections, and model/table creation through the trusted registry and the same authority/transaction discipline. Bound and allow-list model IDs and physical tables; prohibit direct writes outside the trusted path. Invalidate affected reuse metadata atomically and verify live vector rows/evidence at reuse; reject stale evidence. Row triggers on `records` are not a defense against vec0-only changes. Live retrieval must itself validate or consume only authorized, registry-bound vector state; reuse-time checks alone do not protect recall. This is a release gate, not implemented protection.
* **Projection security:** until a separately designed revocable projection mechanism exists, all projection files, manifests, staging files and directories are privileged-only, never served directly to untrusted principals, including after deletion or revocation. Enforce OS/service access controls and fence all alternate serving paths. Authorized APIs must derive responses from current authoritative records and policy, not these stale files. Regeneration is asynchronous and failures remain pending; neither deleting a database record nor acknowledging revocation asserts filesystem or backup erasure. An eventual untrusted projection service would require atomic view invalidation before acknowledgment, fencing existing readers and explicit treatment of open handles, copies and crashes; it is not selected here.
* **Names and consumers:** compare reserved prefixes using ASCII case folding before lookup; `turn-` remains outside this ingestion reservation and its caller-selected/allocated namespace risk is explicitly deferred. Before enabling file projections, reject case-insensitive filename aliases for all IDs within a view, including existing `DOC-`/`doc-` collisions, and inventory normalization/platform behavior; fail preflight rather than overwrite. Audit consumers that infer paragraph neighbors or order from `-pNNNN` identifiers; replace that assumption with the durable structural ordering protocol below before opaque observation IDs are enabled; membership ordinals alone disappear on scrub. Reused bundles, if later enabled, remain shared mutable objects: an authorized participant's mutation can invalidate another's previously returned ID; no independent lifetime guarantee is made.
* **Capacity and audit:** bound outbound reservations globally and per authenticated principal, reserve fairly, expire abandoned reservations with a trusted reaper, and release capacity after enqueue/delivery failure; a stalled client must not hold policy serialization. Rate-limit fresh ingests per principal independently of hidden state. Quotas reduce but do not eliminate distributed denial of service. All fresh-only ingestion job state is request-local memory only in the initial rollout; no durable progress or failed-job API is promised. Required security/operational audit events must be durably recorded or the operation must fail closed where feasible; if audit storage itself fails, signal a generic operational failure without falsely claiming the denial was recorded. Audit existing `ScopeViolation.audit_recorded` consumers and pre-check paths before relying on that contract.

Additional activation tests: case-folded reserved names and filename aliases; forged labels and marker-bearing media sent to external processors; hidden link targets and concurrent link/delete races; correction insertion and vector-only mutation with scrub disabled to exercise independent checks; case-insensitive projection collisions; revocation/deletion with preexisting files and direct-access attempts; principal quota exhaustion and reaping while other principals ingest; all startup and client paths, including recall-disabled routing and privileged journal access. Validate fresh-only hidden-versus-absent behavior across high candidate counts and identical public statuses; independently inspect fresh records, no reuse and no scans.

Additional fresh-only and retirement tests: separately inventory and restrict or explicitly retire legacy hash-bearing provenance, jobs, journals and copies; do not assert their absence or silently rewrite historical evidence. verify the actual fresh schema has no reuse-only candidate index and SQLite/WAL-bound logical artifacts attributable to new fresh-only ingestions contain no reuse-only content hash, canonical request, output manifest or embedding input evidence, and that no durable fresh ingestion jobs are written. Inject a known deterministic legacy ID and forged `done` job; exercise every ingress and recovery route and prove neither is consulted, no inference is skipped on that basis, and no old conflict detail is exposed. Test separately that a fresh retry after unknown commit can create two independently authorized visible bundles; projection retry does not create an ingestion.

Explicit residuals requiring operator acceptance: content-dependent marker refusals can disclose whether a caller-chosen probe matches another scope's marker even with generic denial; principal-based rate limits reduce probing but do not remove this oracle. A principal authorized to create a cross-scope dependent can prevent a narrower principal from deleting the target until an authorized operator resolves the hidden dependent. Do not ignore that dependency or silently orphan it to restore availability. Restricted deletion and break-glass escalation are intentional availability costs, not an erasure guarantee. Concrete queue, transaction and authority deadlines and capacity limits must be selected and load-tested before activation; partitions may still block revocation indefinitely.


## Review resolution: allocation, disclosure, structure and recovery

### Collision-free allocation and policy-sensitive IDs

Fresh IDs require an exclusive allocator namespace, not retry-on-hidden-collision. During fenced migration inventory every existing record ID using the actual comparison/normalization rules and reserve the entire `doc-v5-`, `media-v5-`, and `obs-v5-` namespaces; any existing occupant blocks activation until a separately reviewed namespace choice is made. Generic writes, imports, old binaries and all alternate writers cannot insert in these namespaces. Under the authority lock, allocate from a durable, non-repeating per-namespace counter through a reviewed secret-keyed permutation of the 128-bit space, producing opaque unique tokens; persist counter advancement atomically with publication, and do not expose counter or key. Do not send allocated IDs to processors before durable allocation; allocate all members before evaluating their actual read/write policy; denial of an allocated ID is a request-local policy refusal, never a retry chosen based on occupancy. A rolled-back allocation may be retried only if it was never disclosed or handed to an external processor; otherwise burn it durably. Counter exhaustion is a global capacity failure independent of hidden record occupancy. Key management, namespace isolation, trusted writers, crash/rollback behavior and non-reuse across restores are release gates; reconcile an independently durable allocation high-water mark before unfencing a restored lineage, or block restore. A collision or namespace-invariant violation is corruption: fence the whole store and return generic operational failure, not a candidate-specific retry. This conditional guarantee depends on those verified invariants and does not assert cryptographic perfection or hide timing/resource failures. Test an occupied reserved namespace blocks preflight regardless of visibility, inject corruption and counter exhaustion, and compare hidden versus absent incumbents with ID/link-sensitive markers. A probabilistic random retry loop alone cannot establish exact hidden-occupancy-independent success/refusal.

### Relationships and surviving structural order

At each disclosure, authorize every actual relationship target in the same snapshot. Because conditional redaction itself can reveal hidden-target existence, the initial untrusted representation always omits all relationship fields and relationship-derived counts, existence flags and identifiers, regardless of whether targets are visible, absent or hidden. Do not expose raw records, provenance or other fields encoding these links; authorize and sanitize all derived representations and errors. Traversal may return independently authorized records only through a separately reviewed, hidden-state-independent representation; otherwise disable it. Apply to legacy links and marker/grant drift, query filters, ordering, pagination, counts, projections and alternate routes. Test the same readable legacy record with a hidden, absent and readable target and verify identical relationship representation; test revocation and dangling references.

Preserve structural order independently of scrubbed bundle eligibility: for each new observation persist a validated immutable `(source_id, ordinal)` structural descriptor with the observation, established at publication and protected by the same mutation rules; ordinal is positive and unique per source for a given original ingestion, never renumber survivors. It is descriptive historical placement, not proof of complete bundle membership or authority to expose the source or neighbors. On middle deletion or correction scrub all bundle/membership eligibility metadata as above; preserve descriptors on surviving unchanged observations. A corrected replacement receives an explicitly validated descriptor only under a separately specified correction rule, otherwise it is unordered. Ordered reconstruction uses these descriptors, not IDs, timestamps, or scrubbed membership, and only in a privileged or separately reviewed relationship-safe view; untrusted responses follow the unconditional relationship suppression above. Source deletion and dangling descriptors require the deletion dependency gate; never infer permission from the descriptor. Test middle delete and correction, rollback, gaps, unauthorized neighbors and concurrent changes. Existing legacy ordering requires separately validated legacy handling, not inferred authenticated membership.

### Erasure, confidentiality and privileged remediation

The ordinary delete contract deliberately requires actual target read plus write and authority over all changed dependents. This departs from current contaminated-content erasure behavior: marker drift can make a same-scope record unreadable and hence not ordinarily erasable, even by its writer. A write/delete-only rule with generic errors is not sufficient for noninterference: successful deletion versus generic non-success reveals whether a guessed hidden target exists; a constant success response still changes later observable state and may destroy hidden data. Conversely requiring read protects that boundary but cannot promise ordinary erasure. No solution satisfying both is asserted. A separately authenticated and authorized privileged remediation service may inspect hidden targets and dependents in a protected environment, verify legal/organizational erasure authority distinct from ordinary read access, and perform the fully enumerated atomic effects, or refuse/escalate. Its request, status, audit and results must not expose hidden existence to the ordinary caller; no automatic success receipt, deadline or availability guarantee is offered. Record protected approvals and effects, require the deletion recovery gate, and apply separate retention policy to backups and audit. Test marker-drift-hidden target and dependent, write-only callers, guesses of absent targets, privileged authorization/denial, audit failure and inaccessible remediation. A different blind-erasure API would require a separate threat model, noninterference proof and policy approval before adoption.

### Narrow migration-backup recovery exception

Gate 2 may restore the exact verified backup made under the continuously held external operational fence immediately before migration, only if independently verifiable fence/access-control evidence proves no user, policy-independent data writer, delete, processor handoff or old binary could mutate the authoritative store from the backup snapshot through restore, and no post-backup data mutation or delete was accepted or acknowledged. Migration's own enumerated transactional schema changes are the only permitted database mutations. Capture in the protected migration report the backup identity and integrity verification, lineage and authority snapshot/digest, journal maximum and store version as diagnostic corroboration, fence generation, ownership and a complete access/operation audit; counters or an operator assertion alone do not establish absence of writes. Preserve the verified matching projection snapshot or keep projections fenced pending rebuild. Restore only that backup, recheck integrity, exact schema and data, validate fence continuity and authority reconciliation including any later revocations, then validate allocation high-water and all access boundaries before unfencing. If any proof is missing, lock continuity uncertain, a write/delete accepted, or backup identity ambiguous, this exception does not apply: stay fenced and require the general independently durable data-history/ledger protocol. Drill successful restoration and injected post-backup deletion, fence loss, divergent authority and tampered backup; each failed precondition must remain fenced. This exception does not authorize general old-backup recovery.

### Availability and further operational gates

The selected authority lock remains exclusive per store for reads as well as writes, prioritizing simple disclosure/revocation ordering over concurrency; shared-read locking is an unselected alternative requiring a separate proof covering deletion, mutable policy and handoff ordering. Enforce request-local cost, input and per-principal concurrency budgets independent of hidden counts, and cancel local overruns safely as above; scan work may still depend on hidden rows, so bounded latency and absence of resource channels are not claimed. Load-test worst admitted searches, lock hold times and revocation latency, and block activation without an explicit service-level decision; partitions or uncertain fencing can make the store unavailable indefinitely. For external embedding authorize each irrevocable handoff (or an explicitly authorized bounded batch) under current authority; no network I/O while locked. Provide only a privileged, access-controlled duplicate-detection report for ambiguous fresh retries, without automatic deletion or untrusted counts.
