# Trusted-local alpha: product and security boundary

**Decision:** On 2026-10-28 the operator selected a simple trusted-local alpha over requiring the proposed separate coordinator and independent external authority for every installation. This is a product direction and implementation target, not a statement that the current working tree meets these requirements or that an alpha is approved.

## Intended experience

One person installs and operates Weft on a device they control. Memory is local by default, understandable, inspectable, correctable, exportable and deletable. Local models are the default; external model processing requires explicit informed user consent showing the provider and data involved. The intended desktop should make these controls accessible without requiring a command line. Self-hosted and multi-user service modes are future work, not implied by this decision.

## Trust boundary and limitations

The first alpha is a single-user local application, not a network service. The person and code running as that OS user are trusted; Weft does not claim protection from malicious same-user processes, administrators, compromised devices, or direct database access by such processes. File permissions do not create isolation between same-user profiles. A device compromise or unprotected backup can expose plaintext memory. Local storage alone is not encryption, and an exposed service would require separately designed and verified authentication and isolation.

The stronger design in `vector-identity-consolidated-proposal.md` remains a proposed possible future tier, not an alpha prerequisite or an approved specification. This decision does not adopt its separate OS identity, independent external ledger, or whole-host rollback detection. Nor does it waive data integrity, deletion, provenance, or scope defects within the local trust boundary. Do not imply protection against historical rollback, backup resurrection, physical erasure, timing side channels, or external-provider retention unless a specific mechanism is implemented and tested.

## Minimum release obligations

1. **Sources and inspection:** Users can identify what was imported, what memory was derived, and the evidence supporting it; derived material is labelled and does not become a user decision merely because an agent or document asserted it.
2. **Isolation and recall:** Scope authorization precedes disclosure; data outside the requested scope must not be surfaced as a result. Detect and address known same-scope visibility and candidate-selection issues relevant to supported use; do not claim untrusted-client noninterference based only on single-user tests.
3. **Vector integrity:** Document and query embeddings use a compatible, identifiable generation. A stale, mismatched, missing, malformed or nonfinite vector must not silently count as valid or produce a misleading success. Model/config changes and incomplete indexes need an explicit tested rebuild or refusal path. A model-reported name or row count alone is not evidence of correct generation. Specify exactly what is and is not authenticated under the local trust model.
4. **Deletion and recovery:** Deletion must remove or invalidate applicable live records and derived searchable artifacts, with tested behavior for retry, interrupted writes, corrections, indexes and supported recovery paths. State whether source files are affected. Clearly disclose residual copies in WAL, free pages, external providers, exported files, and backups as applicable. Do not promise secure erasure or deletion across backups without a mechanism. Backup/restore must not silently resurrect deleted data; if a safe reconciliation mechanism is unavailable, refuse or clearly block the affected restore workflow rather than calling it safe.
5. **Import and processing:** Imports have truthful success/failure reporting and durable atomic behavior for the supported paths. Model errors and unsupported formats are visible. Machine-generated media descriptions or transcripts must be labelled; external processing needs the consent above. Do not assert visibility-isolated or untrusted-service ingestion guarantees before those designs are implemented and verified.
6. **User control:** Provide an actual supported way to inspect, correct, export and delete memory, with accessible product UI before a public-facing desktop release. A CLI-only prototype is not that desktop. Backup and restore need clear guidance and verified limitations.
7. **Security defaults:** Owner-only permissions on newly created local data where supported, no unauthenticated network listener, minimal and explicit outbound traffic, and no silent remote fallback. Plaintext-at-rest and same-user limits must be visible to users.
8. **Verification and release:** Tests cover real supported paths, positive and negative authorization, vector generation changes, deletion/retry/recovery, failure atomicity, and packaging. Run a real-model end-to-end test when artifacts are available and distinguish it from fake-adapter tests. Independently review a frozen implementation, resolve or explicitly accept residuals with the operator, and complete the alpha gate before calling it usable. Phase boundaries, commit/review authority, and the clean-room protocol continue to apply.

## Next work

Inventory existing uncommitted work and map each applicable integrity problem to a concrete local-boundary invariant, a reproducing test, a minimal implementation and verification. Keep untrusted-service designs explicitly deferred. Prefer vertical, test-first changes and do not claim the release obligations are met until exercised. Freeze and present the resulting phase for a separate independent review; this decision does not itself authorize release or waive the phase gate.
