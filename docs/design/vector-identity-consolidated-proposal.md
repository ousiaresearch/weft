# Vector identity and disclosure: single-user per-profile contract

**Status: proposed high-assurance consolidation, not implemented, approved, or adopted as a first-alpha requirement.** This is a candidate replacement for the original proposal and all four appended review rounds in `docs/design/vector-generation-identity.md`, not a second operative contract. MUST, MUST NOT and BLOCK express this proposal's requirements, not claims about current Weft. It retains a distinct-OS-identity coordinator and independently durable external authority: those are stronger, more costly guarantees than the stated single-user deployment goal necessarily requires. The operator has not selected that tradeoff. Separately assess a simpler trusted-local alpha with explicit residuals before adopting either boundary; neither option may weaken actual deletion, provenance, or rollback claims. No implementation, schema, OS isolation, review, migration, distribution or product admission is implied. A frozen contract and applicable implementation require later independent adversarial review and operator phase approval.

## 1. Scope, intended authority and outcomes

One trusted local user operates one independently selected profile/instance at a time; one store may have multiple scopes and at most one ACTIVE vector generation per scope. This is not a multi-user or untrusted-service release. A privileged or malicious same-user actor able to defeat the OS boundary is outside the threat model; accidental wrong-profile routing and admitted/old-process bypass are in scope. The separate `visibility-isolated-ingestion.md` gates remain mandatory for any untrusted-service claims; this design does not satisfy them.

The operator explicitly chooses the intended instance through a launch argument or host-managed configuration independent of ambient profile environment, resolver and profile-relative capability discovery. Before every operation, the authenticated coordinator compares that pin with the presented instance-bound capability, resolver result, independently provisioned authority record and store binding. Missing or mismatched intent fails without mutation or disclosure. The capability is obtained through that independently pinned channel, not by first resolving the ambient profile. Same-user profiles are not inherently isolated by file permissions; protection from ordinary processes requires the actually enforced coordinator identity/sandbox boundary. This is an accident-prevention contract, not a hostile-same-user isolation claim.

The coordinator owns an exclusive store-wide mutation/disclosure fence and is the only admitted authority for DB, WAL/SHM, vector files and relevant authority files and containing directories. An independently enforced distinct OS identity or equivalent sandbox must prevent normal clients, old binaries, utilities and direct SQLite opens from bypassing it. A lock, trigger, version marker or profile path alone is not a fence. If the real boundary cannot be demonstrated, all serving and writes, including fresh stores, are blocked. A privileged diagnostic is read-only, outside recall, and operates only through the enforced boundary.

Grants and policy for the single authorized principal live in authoritative store state and are changed only through the coordinator. A separate revocation source is not ordered by this contract and is disabled unless integrated into this same fence and epoch protocol. A scope is an authorization boundary, not a model-generated assertion. On uncertainty, generic unavailable is returned; operator diagnostics must not expose record IDs. An explicitly requested and labeled lexical mode may operate only if its own requirements in §5 are satisfied; hybrid never silently falls back to lexical.

## 2. Generation, artifacts and per-row identity

A strict, canonical, versioned descriptor and its full digest bind the actual allow-listed model, tokenizer, configuration and artifact bytes; trusted adapter and preprocessing code; library, quantization, runtime, kernel, device and platform inputs that affect output; dimensions, normalization, metric and canonical little-endian IEEE float32 format; document extraction, fencing, paragraph algorithm, source mode and truncation; and the separately specified query preprocessing and compatibility predicate. Unknown fields, encodings, versions, duplicate keys, nonfinite values or unclassified output-affecting inputs block activation. Choose and document one meaning for simultaneous centroid and head before admission; until then reject both enabled. A runtime or artifact change requires a new generation unless a separately reviewed, model-specific validated compatibility predicate permits it.

A trusted factory binds both document and query execution to the same verified generation and its separately defined contracts. Self-reported model IDs or adapter descriptions do not prove identity; custom unverified adapters cannot write durable vectors or contribute to completion. Experiments remain isolated, disposable and non-promotable. Copy the exact allow-listed load inputs to a private content-addressed snapshot, hash the final snapshot and load only from it; validate symlinks, file identity and digests and prevent admitted writers from changing it for the whole model lifetime, including lazy loading and mmap. If immutability cannot be enforced and tested, stop generation and query embedding.

The authoritative SQLite registry maps full scope and descriptor to collision-checked physical table identity, exact DDL, dimension, lifecycle and one active activation. Never infer ownership from truncated names. Unknown/missing tables, DDL, versions, mappings or shadow objects fail closed. Registry, evidence and vec0 data are changed in the same verified SQLite transaction. Physical names are reserved even for retired or quarantined objects.

Each eligible vector requires authenticated evidence over a versioned, domain-separated, length-delimited canonical frame including profile/store and lineage, full scope, physical table identity and vec0 row key, record key and non-reused incarnation and revision, canonical input digest, generation descriptor and non-reused activation, dimensions/format and the exact stored canonical float32 bytes. Coordinator-only keyed MAC or independently authenticated external-history commitment supplies authority; an unkeyed digest alone does not. Exclusion evidence authenticates applicable identity, source revision, input, generation and a closed nonsecret reason catalogue. Exact codec, widths, digest/MAC algorithms and key lifecycle are blocking deliverables. Evidence records provenance, not mathematical proof of correct inference.

Both model outputs are materialized to owned immutable canonical bytes, validated for dimension, float32 representability, finiteness and generation-specific metric/normalization constraints, and only those bytes used. Verify actual deployed sqlite-vec bytes and mapping on publication and every eligible use. Batch results are associated using unique explicit record/input keys, not unverified position. Swapped mappings, duplicate, missing, malformed, inconsistent or unverified evidence block use.

## 3. Inventory, eligibility and visibility

The coordinator derives the caller-independent complete integrity set from authoritative scoped records in one SQLite snapshot using a versioned deterministic eligibility and extraction function. Every relevant record must have exactly one valid vector/evidence pair or a valid generation-bound exclusion for an approved non-policy reason. Policy visibility is never an exclusion. Compare exact keys, not just counts: every physical row and evidence row in the active table must map one-to-one to an eligible record and match its scope, table, key, generation, source and bytes; missing, extra, duplicate, orphan, ineligible or mismatched data is an integrity violation. Do not rank or limit before this validation. Non-active objects are inventoried against their declared state and reserved ownership.

A versioned visibility function evaluates every scope member against authoritative policy in the same snapshot. Hybrid is admitted only when all members have one uniform visibility class for the principal and that class is authorized; mixed or withheld scope membership blocks hybrid, even if the record might otherwise be excluded. Any record, policy or grant change affecting membership, visibility, ranking or evidence advances the non-reused scope epoch under the mutation protocol. The disclosure fence checks that epoch and authorization again. A new withheld member may therefore make a previously available scope unavailable.

For this release, any unexplained authority, bypass or inventory anomaly fences the whole store, including anomalies in non-active artifacts, until authenticated recovery determines safe disposition. Disclosure and normal writes, including delete, are blocked; a delete is not acknowledged or implicitly queued. Only authenticated bounded diagnostics and explicitly authorized recovery/restore or cleanup operations admitted by the recovery protocol are allowed while fenced. This is deliberately conservative: narrowing the fence based only on an artifact's label is unsafe until independent ownership, deletion and cross-table effects are proved. Corruption and mixed visibility can change availability and are not hidden-membership noninterference or timing guarantees. Do not claim physical erasure of backups, free pages, WAL, SSD or shadow tables.

## 4. Authority, closed operations and mutation ordering

Every durable object and write path must be classified in a versioned manifest. AUTHORITY includes records, source links, grants/policy, membership and epochs, registry/lifecycle, exclusions, vector evidence/bytes, operation markers, identity/lineage and any audit or backup catalog that controls recovery. DERIVED objects, including FTS, job state, caches and ingestion bookkeeping only if proved non-authoritative, are disposable: they cannot by themselves establish eligibility, completion, authorization, provenance or recall; FTS candidates must be verified against authoritative records and index completeness must be rebuilt or independently verified before lexical results are served. Derived updates are either catalogued with their authoritative operation or have an explicitly reviewed, fenced disposable rebuild path that cannot change authoritative outcomes. No unclassified object, mutator, effect, trigger, virtual/shadow table or executable writer may be admitted; startup self-check fails closed. Triggers/constraints on ordinary tables are backstop invalidators/detectors only; they do not allocate authority or prove bypass absence and cannot be assumed to survive rollback. Cover deployed `REPLACE`, recursive triggers, pragmas, extension availability and actual vec0 behavior. Direct vector writes are possible only through the fenced verified wrapper.

The following is the normative closed operation-class inventory; before enabling any row, a reviewed versioned catalogue MUST enumerate each concrete API and exact authority/auxiliary effects, caller authority, canonical request and intent fields, marker, allocations, abort, outcome and restore handling. Incomplete rows block that operation and its dependent release path. All rows use the exclusive fence, externally authenticated intent and matching SQLite marker/commit and external finalize or valid abort, except a separately reviewed authority-only operation whose equivalent atomic externally durable marker is explicitly defined. No implicit maintenance exemption exists. `BLOCK` below is the conservative restore default, not a claim that replay exists.

| Class | Examples / effect | Restore disposition before detailed protocol |
|---|---|---|
| GENESIS / enrollment | fresh store binding and baseline, initial identities | BLOCK absent authenticated genesis and complete baseline |
| Content and link mutation | ingest, correction, overwrite, source/link change, record incarnation/revision | BLOCK unless complete authenticated payload and idempotent replay proved |
| Delete | delete record and invalidate/remove associated live evidence and vectors | REPLAY by incarnation only after reviewed payload and idempotence; otherwise BLOCK |
| Authorization | principal, grant, policy, scope membership, revocation | REPLAY only with complete authenticated payload and ordering; otherwise BLOCK |
| Vector and eligibility | publish/replace vector, exclusion and evidence, epochs | INVALIDATE affected generation and rebuild; authoritative source effects still reconciled |
| Generation lifecycle | build chunks, validate, activate, retire, fail | INVALIDATE staged/affected evidence and rebuild unless exact replay is proved; never reactivate retired/failed |
| Schema / coordinator upgrade | schema, manifest, trigger, supported binary changes | BLOCK unless exact compatible migration/replay is reviewed |
| Trust base | capability issue/scope/revoke, key creation/rotation/revocation, authority or coordinator configuration | BLOCK unless key/capability lifecycle and replay are reviewed |
| Recovery / restore / clone | reconciliation decision, recorded orphan abort, restore lineage, explicit new-lineage import | BLOCK absent approved ceremony and complete independent authority |
| Retention / cleanup | backup catalogue, ledger retention/compaction, quarantine or retired-table cleanup | BLOCK unless protected backup, ownership, deletion policy and retained-history obligations are proved |

Epoch and identifier changes are effects of their enclosing operation, not free-standing unlogged mutations. Atomic append of the operation intent reserves all needed non-reused identifiers and records the externally assigned ledger operation ID; this one primitive removes allocation circularity. The high-water is derived from authenticated history. Every reservation, including aborted, orphaned or ambiguous attempts, is permanently burned. Overflow, collision, incompatible history or unprovable allocation fences the store. GENESIS consumes a pre-provisioned independent binding; it does not create its own proof of operator intent. External reservation/append atomicity, bootstrap and crash windows are implementation gates.

A client supplies a unique request/idempotency token before an operation, scoped to the authenticated capability and canonical request. The external authority assigns an operation ID at intent append; intent, SQLite marker, finalize/abort and outcome bind **both** identifiers, request digest, store/lineage and fence ownership. Lookup is authenticated by the caller-known token, including after crash. Same token and request returns the recorded outcome without reapplying; same token with different request is rejected; an unresolved outcome stays unresolved and is never retried as a new mutation. Define durable retention at least through the permitted retry/recovery horizon and prevent reuse after expiry; without a proved expiry/tombstone rule, retain the identity and reject ambiguity.

Ordinary embedding pipeline: under a consistent read and appropriate authorization capture profile, source incarnation/revision, canonical input, active activation and policy; only content authorized at capture enters the trusted embedder. Compute and copy/validate output outside the SQLite write transaction and outside the ordinary exclusive fence. Reserve bounded outcome handoff capacity, acquire the fence, reconcile external authority and revalidate all captured identities, input, policy and generation. Changed inputs or revoked authorization discard output; retry is bounded. Validate the proposed complete effect before the intent, then atomically append the intent/reservations, `BEGIN IMMEDIATE`, repeat checks, write exact bytes, evidence, epochs and matching marker, commit with verified durability, append external finalize, and enqueue the immutable outcome under the fence; release SQLite then fence before any network I/O. All admitted mutations use this same fence before SQLite writes, with no gap for source correction, delete, vector, grants, maintenance or other writes. No transaction may rely on a Python lock alone.

Before COMMIT is issued, a live coordinator holding a validated fence may append an authenticated ABORT for a deterministic rejection or confirmed rollback; it binds intent sequence, external operation ID, request token, intent digest and fence-owner token and consumes reservations. No abort after finalize or finalize after abort is valid. Once COMMIT has been issued, a connection error is not proof of rollback: fence and reconcile using a fresh connection and independently durable histories. A missing marker alone is not sufficient proof to abort unless the reviewed protocol establishes database identity, durable visibility, fence continuity and absence of an in-flight/late commit; otherwise remain fenced. Crash-orphaned intents require the audited recovery ceremony. Never acknowledge an uncertain mutation. This intentionally rejects the review suggestion that a fresh-connection marker check alone automatically proves abort safety.

## 5. Query, lexical mode and handoff

For hybrid, construct the verified query embedder from the bound snapshot, compute outside the fence, and validate immutable canonical query bytes and compatible query descriptor. In one SQLite read snapshot capture lineage, activation, scope epoch, policy and record revisions; perform full integrity, eligibility and visibility checks before ranking. Reconcile the snapshot's authoritative state and operation markers with independently authenticated external-history expectations. Reserve a fixed maximum response capacity before acquiring the exclusive fence, with separate bounded read and mutation/revocation pools. Reject reads promptly during observed maintenance; release reservations on retries. Under the fence, recheck binding, authority/history, activation, epoch, authorization and final candidates/bytes, and commit the immutable response to a trusted, bounded irrevocable handoff addressed to the authenticated recipient. A changed token triggers bounded retry then generic unavailable. Fence, reservation and enqueue deadlines and writer progress require measurement; no client-controlled I/O or queue waiting under the fence.

A full snapshot comparison plus an under-fence shortcut is permissible only if a separately reviewed detector proves no unadmitted changes can evade it on the actual deployment. SQLite `data_version`, file timestamps, a ledger head or an epoch alone are not presumed sufficient. If proof of the no-gap property is unavailable, perform the necessary complete check under the fence subject to measured deadlines, or block serving. Never relax the fence or accept a known bypass for performance.

Explicit lexical retrieval uses the same independent profile pin, authorization, snapshot, current policy/epoch, deletion ordering, bounded reservation, fence revalidation and handoff. Its label is lexical; it cannot claim hybrid completeness. FTS must have verified completeness and record correspondence or be reconstructed from authority before use; post-filtering an incomplete or stale index is insufficient to claim complete results. A lexical implementation that cannot meet this contract is unavailable, not a fallback.

The irrevocable trusted enqueue is the disclosure and successful local acknowledgement linearization point; successful delivery over a network is not promised. An effect committed and finalized before a crash may have no enqueued outcome: authenticated token lookup resolves it. A deletion ordered before response enqueue prevents that response; a response enqueued first can arrive after deletion acknowledgement, even from a stalled client. Queue exhaustion does not hold the fence while waiting. These bounds are not an end-to-end delivery deadline or a secrecy/timing guarantee.

## 6. Rebuild, legacy and retention

Generation transitions are BUILDING → VALIDATED → ACTIVE → RETIRED or BUILDING/VALIDATED → FAILED; RETIRED and FAILED never reactivate. Each attempt and activation uses fresh non-reused identity. Rebuild is offline under an exclusive store-wide maintenance ownership token: no normal serving, mutation or acknowledged deletion; other requests time out unavailable. Only the owner may stage bounded chunks without recursively reacquiring the fence; external intent/finalize applies to each staged operation. Model computation may run during this exclusive maintenance interval, so long rebuilds reduce availability; chunking and measured limits are required, not a promise of bounded total rebuild time. Staging is never queryable. Activation is one transaction after exact current-source, vector and evidence reconciliation; crash or ambiguous commit keeps the store fenced until audited recovery inspects registry, physical/shadow objects and both histories. No automatic deletion of unknown objects.

Fresh-store genesis is permitted only after independent operator provisioning and the genesis gate. Legacy enrollment/migration is **blocked for this first release**: historical vectors, job rows, model IDs and table names cannot supply provenance or prove past deletions. An operator-attested baseline is not deletion history and cannot override this block. A later separately approved migration design must use no-create read-only preflight, exact inventory of SQLite/vec0/FTS objects and WAL/sidecars, enforced old-binary fencing, protected consistent backup, schema migration separate from rebuild, and a deletion-history-safe source; recognized old vectors are quarantined, not queryable or reused. A separately authorized new-lineage import from independently authoritative sources requires proof against resurrection, not merely an operator attestation. No automatic cleanup.

Delete atomically removes or invalidates affected vectors/evidence in every accessible live generation under the fence; inaccessible retained artifacts are disclosed as residuals and cannot reactivate. Retired, failed and quarantine tables, WAL, free pages and backups may retain sensitive material. Cleanup requires known ownership, verified backup, explicit authorization and a reviewed retention/deletion policy. No physical-erasure claim beyond tested behavior.

## 7. External history, recovery and restore

The external authority is independently authenticated and durable outside the database and its backup/rollback domain; the coordinator identity, storage independence, authenticated append, allocator, replay material, fresh head and durability assumptions must be proved. Intent, SQLite marker/effects and finalize form a write-ahead protocol; an intent alone is not success. Reconcile intent-only, SQLite-committed/not-finalized, finalized-ahead, database-ahead, conflicting abort and unknown outcomes under the fence. Unexplained database-ahead or history divergence remains fenced; no trigger or re-embedding launders bypass. Whole-host rollback can roll back a co-located ledger and DB together: detection of that event requires an independent off-host witness or equivalent independently protected monotonic authority. Without it, explicitly disclose this undetectable residual and do not claim whole-host rollback detection.

Restore enters fenced `RESTORE_RECONCILE`: verify authenticated backup lineage and exact consistency point, independently fresh external head, complete authenticated suffix, allocator high-water, operation outcomes and retained payloads. Apply only reviewed idempotent replay dispositions in §4, including deletions and grant revocations, by incarnation; invalidate affected vectors/evidence and rebuild, burn all reserved identifiers and finalize a new restore-lineage record before service. Any BLOCK operation, missing suffix/payload, history compaction gap, uncertain authorization or divergent state blocks restoration; no operator override can assert missing evidence. New-lineage import requires independently authoritative source and proof deleted records will not reappear. Ledger retention must cover every backup advertised as restorable; compaction is catalogued and cannot strand one silently. A coordinated external/DB commit protocol, genesis, restore, replay, abort, compaction and key lifecycle are not yet specified to implementation detail and are mandatory blocking gates.

## 9. Acceptance verification derived from this contract

All tests exercise production entry points, actual target OS identities, independent processes/connections and deployed SQLite/sqlite-vec, not only mocks. They verify observable state from fresh connections and both independent histories. Process-kill tests do not prove power-loss durability.

1. Pin A with environment/resolver B and same-named scopes; fail without mutation or disclosure; capability discovery cannot follow B. Test missing, wrong, revoked and cloned capability and actual old binary/direct opens against fresh stores and maintenance.
2. Reject changed artifacts, tokenizer, runtime, model/query/document preprocessing, dimension, metric and unknown descriptors; prove asymmetric compatibility when intentionally supported, both-mode rejection, lazy-load mutation and unverified adapter refusal.
3. Inject finite stale vectors, nonfinite/overflow, reused mutable buffers, field or duplicate-content row-mapping swaps, wrong table/key and positional batch misassociation; verify exact canonical bytes and atomic rollback. Force table-name collisions, missing and unknown physical/shadow objects and DDL.
4. Compare physical/logical key sets; positive clean control succeeds, orphan/extra/missing and non-active ownership anomalies yield generic unavailable and store fence, not unchanged success. Test uniform, mixed and withheld policy, exclusion reasons, and policy/epoch changes. No absent-versus-hidden timing guarantee is tested or claimed.
5. Enumerate all actual mutators and durable objects against the catalogue/manifest; inject unauthorized direct SQL for each authority class, `REPLACE`, missing extensions and disabled pragmas. Test derived jobs/caches and FTS cannot grant completion or disclose deleted records. An unclassified object or path fails startup.
6. Race delete/recreate, correction, revocation, generation away/back and independent-process mutation against capture, inference, snapshot, final recheck and enqueue using deterministic barriers; deletion during inference prevents publish. Test no gap between snapshot and handoff, including unadmitted write attempts. Lexical deletion ordering and explicit lexical label use real entry points.
7. Inject failures before/after intent/reservation, BEGIN, every write, COMMIT issuance, durable commit, finalize and handoff. Test valid pre-COMMIT abort, invalid abort/finalize ordering, connection error with ambiguous commit, fence-owner death, lost outcome, same-token retry, different-request token reuse, burned identities, overflow and restoration after burn. Inspect external operation ID and caller token in all matching records.
8. Saturate read reservations and stall clients; mutation/revocation has reserved capacity and makes measured progress. Test bounded retries and full queue without disclosure or fence-held waiting; test both deletion/handoff orderings and delayed delivery of already enqueued bytes. Measure worst-case scan and fence hold by corpus size; block workloads exceeding safe limits.
9. Kill rebuild at staging/validation/activation, inspect orphan ownership, no concurrent normal writes, no acknowledged delete during maintenance, explicit recovery and never-reactivate rules. Inject SQLite and extension DDL/DML failure including commit ambiguity; verify records, FTS, vector, registry, evidence, audit, jobs and schema after reopen.
10. Restore authenticated backups after deletion, correction and revocation with complete suffix; test missing/truncated/stale history, expired retention, wrong lineage, DB rollback, external authority outage, bypass and clone/allocator ABA. Test off-host witness when whole-host rollback detection is claimed; otherwise document the residual. Ensure unproven records are never silently resurrected.
11. Before release, run focused regressions, a real-model end-to-end case and `scripts/test.sh`; independently review the frozen implementation and measured deployment evidence on a later turn. Document any unsupported OS/runtime, backup, migration and physical-erasure residuals.

## 10. Explicit unresolved implementation and release gates

None of these components is asserted to exist or work. Admission requires all applicable items, independently reviewed and verified, then explicit operator phase approval:

- Actual distinct-identity/sandbox coordinator, provisioned explicit profile intent and scoped capabilities, complete process/filesystem and old-binary fence, crash/owner recovery and denial tests on every supported OS.
- Strict generation/eligibility/visibility descriptors; closed runtime and artifact manifest; immutable snapshot implementation; trusted factory; real float32/vec0 codec/readback, keying, evidence and authenticated exclusions; exact registry and schema/trigger/pragma manifest.
- Exhaustive concrete operation/effects catalogue and classification, connection proof and independently validated no-bypass/no-gap detection, including derived FTS; closed trust-base, cleanup and maintenance operations.
- Independently durable authenticated external authority, atomic intent-plus-ID reservation, genesis bootstrap, operation ID/token retention and deduplication, intent/marker/finalize/abort state machines, cross-store crash safety and real durability assumptions.
- Full authenticated replay/restore, retention/compaction, backup consistency, bypass recovery, deletion/retention policy and optional independently witnessed whole-host rollback detection; legacy migration is not enabled in this release.
- Actual bounded handoff, queue capacity partitioning, authorization/epoch synchronization, deletion ordering, deadlines and progress; real scale measurements and acceptable commercial performance without weakening correctness.
- Frozen implementation, production-path regression and integration tests, independent later-turn adversarial review, resolved blocking findings, and explicit operator approval. If any required mechanism is absent or uncertain, fail closed; no per-profile alpha or commercial-release safety claim follows from this document.
