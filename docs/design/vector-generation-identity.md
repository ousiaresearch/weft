# Vector generation identity for the single-user alpha

**Status:** Proposed design, 2026-10-28. Not implemented, reviewed, migrated, or a release guarantee. Applies to the per-profile, trusted-local test; it does not replace the untrusted-service gates in `visibility-isolated-ingestion.md`.

## Problem and evidence

The current vec0 table name uses truncated hashes of scope and `model_id`. Neither the full model identity nor artifact bytes, tokenizer, pooling, query/document preprocessing, document source representation, or physical table ownership is recorded as authoritative generation evidence. `vector_index_complete` checks readable rows and currently rejects nonfinite values, but a present finite vector may still be stale, mislabeled, wrong-model, or inconsistent with its source. An embedder may claim any model ID. Re-embedding on a retry affects only that document and does not fix other rows. Completeness and nearest-neighbor search are separate operations and currently lack a common SQLite read snapshot. Tests of SQLite/vec rollback are necessary but do not establish provenance or a full migration protocol.

## Scope and security boundary

Initially support one active vector generation per scope in one profile-owned store. Unknown legacy vector state fails closed for vector/hybrid recall and new vector writes; lexical operation, if explicitly enabled, must not silently masquerade as hybrid. Do not delete records, vectors, or backups automatically. A privileged same-user process or direct database writer is outside this boundary. Preventing such processes from changing artifacts/SQLite, or isolating untrusted principals, needs a separate OS/service authority boundary. A profile-scoped path alone is not that boundary.

## Proposed generation contract

1. A versioned strict canonical descriptor records full actual artifact digest(s), tokenizer and config digests, trusted adapter/implementation identity, vector dimension, dtype, pooling, normalization and distance metric. Define exactly which artifact files are read and hash all of them; a snapshot directory name, shortened revision, caller-supplied model name, or hash of configuration alone is insufficient. Preserve the canonical descriptor as well as its full digest. Unknown descriptor versions, duplicate keys, noncanonical encodings, nonfinite values, missing fields, or unclassified configuration must fail closed.
2. Bind document processing to the generation: extraction/fencing and paragraph algorithm versions, source mode (centroid, head with exact truncation, or absent), and effective precedence. The option with both centroid and head enabled must either be rejected or have one explicit tested meaning. A model can support different query and document preprocessing: record a separate query contract and explicit compatibility predicate rather than assuming identical descriptors or inferring compatibility from a model name.
3. Select the descriptor through a trusted in-process factory bound to the actual execution and immutable local artifacts. A custom adapter's self-reported descriptor is not proof. For trusted-local alpha only, either restrict to the adopted verified embedder or label custom adapters unverified and disallow them from durable vector generations. Establish how artifacts are held immutable across validation and model loading; if that cannot be established, block activation. This protects against accidental drift, not a hostile same-user actor.
4. Registry is an authoritative mapping of full scope and full generation descriptor to an allocated, collision-checked physical vec0 table. Do not infer ownership from truncated table hashes. Registry records a unique active generation per scope; schema/version, physical table DDL, dimension, model and descriptor must be verified on every safe open and use. Canonical fields, constraints, allocation and SQLite DDL are implementation deliverables, not an existing schema. An explicit generation transition is an offline rebuild, not a silent update.
5. Each vector must be tied to its authorized record, current canonical embedding input and active generation. A scope-wide flag cannot prove that every row was generated correctly while generic `vector_put` or other mutation paths can overwrite it. Either gate all writes through the verified generation path and atomically maintain per-record input evidence, or retain per-vector input/generation evidence and validate it on use. Evidence establishes recorded provenance, not mathematical correctness. Define authorized correction, overwrite, deletion, source-link and content mutations so stale vectors cannot survive. Direct writes must not be able to assert arbitrary provenance.
6. Query embeddings are validated for dimension, finite float32 representation and compatible query contract. Read active generation, indexed records and candidates in a consistent SQLite read snapshot; handle artifacts/model calls outside that snapshot using an epoch or equivalent generation recheck before returning results. A model call does not grant scope. Unknown, incomplete or inconsistent state fails closed and yields a diagnostic without exposing hidden record IDs.

## Legacy and migration contract

- Existing stores contain no trustworthy generation evidence. Do not backfill provenance from table names, model IDs, job rows, apparent completeness, or current configuration. Empty and populated vec0 tables—including sqlite-vec shadow tables—must be inventoried explicitly. Unknown tables, triggers, schema versions and inconsistent mappings block migration. Preserve the old DB and explain what needs rebuilding.
- Existing constructors currently run mutating initialization before checking migrations and older binaries can accept future versions. A no-create, read-only preflight and explicit operator-authorized offline migration must precede schema mutation; prove handling of WAL/sidecars. Freeze and fence all old binaries and SQLite access paths using an enforced OS/service boundary before migration. A version marker alone is not an old-binary fence.
- Back up the full SQLite-consistent store and independently protected external artifacts. Rebuild from authorized authoritative source records using the exact validated generation, without treating historical vectors or jobs as provenance. Specify backup retention, deletion recovery and explicit operator approval; do not silently resurrect deleted records through restore.
- Use a migration transaction with exact schema and data validation, no `executescript`-induced implicit commit, and real deployed sqlite-vec behavior checked. Test failpoints at registry, table DDL, vector data, evidence, version and commit boundaries. Verify rollback and separately reopen the committed store. Ambiguous commit must not be reported as success. External files and artifacts are not transactionally covered by SQLite.

## Concurrency contract

Compute document embeddings outside the SQLite write transaction only after the actual input and processor are authorized. Then use `BEGIN IMMEDIATE`, reread and validate active generation, source records, content versions and authorization, and atomically write records, vectors, evidence and completion state. Reject any changed generation/input. Any deletion, correction, overwrite and allowed direct vector path must participate in the same serialization and invalidation rules. A Python `RLock` alone does not protect independent connections. Query completeness, eligibility and candidate reads must use one consistent read snapshot; test races against update, deletion, generation switch and rebuild. Policy revocation and untrusted-service claims still need the separate authority design.

## Review round 1: required contract clarifications

The frozen `0317d6411e405b71b328a350b682bf2fe6110482f4438559e4e354b888e3b804` received two REQUEST_CHANGES reports. Johann's later instruction selects GPT-6.1 Terra and Claude Sonnet 5.5 for Weft reviews, superseding the earlier GPT-5 Codex preference. These are design findings, not proof of an implementation defect or gate approval. This section resolves the contract direction for the next review; every mechanism remains an implementation and verification gate.

- **Profile binding:** An independently provisioned instance identity bound to the trusted profile resolver must be checked against immutable store metadata on every read/write/backup/restore entry point, including same-named scopes in different profiles. A path or a field stored solely in the database is not independent evidence. An explicit operator-controlled clone/import or recovery ceremony establishes a new binding; accidental wrong-store selection fails without mutation. Same-user hostile access remains outside this accidental-routing guarantee.
- **Document outputs and evidence:** Validate every document and query vector for dimensions, finite float32 representability and generation-specific normalization/metric constraints before publication. Refuse missing, mismatched or malformed per-vector evidence; generation completeness and every recall-serving read must validate it for each eligible row, not merely check row presence. No unverified adapter output or its derived artifacts may enter a durable index or influence completion. Pure transient experimentation must use an isolated disposable store and cannot be promoted as verified data.
- **Registry authority:** The registry, active generation, per-vector evidence and vec0 tables live in the same authoritative SQLite database and change within the same verified transaction. Every open or entry point that can read/write or contribute to recall, backup or restore validates the binding, schema and active generation; a privileged diagnostic-only raw reader may inspect without conferring a usable or trusted status and must not feed recall.
- **Artifact stability:** Materialize the exact allow-listed load inputs in a private content-addressed snapshot through a trusted, validated copy process, then hash the final snapshot and load exclusively from it. Prevent changes through all admitted writers for the entire load/generation interval and verify file identity, symlinks and digests on load. Merely chmod-ing a directory or hashing before reopening does not prove immutability against same-user writers. If the deployed OS/runtime cannot enforce and test this contract, block vector generation rather than assert it. Hostile same-user compromise remains out of scope; accidental mutation through admitted processes is in scope.
- **Mutation/ABA fence:** Assign each record incarnation, mutation and generation activation a non-reused identity or revision under the authoritative write serialization; deletion/recreation and generation-away/back must never restore an earlier token. The allocator must specify overflow, collision, restore/rollback and cross-instance behavior; uncertainty fences the store. Capture actual record incarnation, revision, input and generation activation before model work, then compare them under `BEGIN IMMEDIATE` before publishing all effects. Validate at every permitted writer, including correction, deletion and direct vector paths. Test delete/recreate and switch-away/back with independent connections and deterministic barriers.
- **Query handoff:** Define the disclosure linearization point as an irrevocable, bounded handoff by a trusted local coordinator. Read a consistent SQLite snapshot and record the active generation activation and a mutation revision covering every candidate and permission relevant to the result. Reserve handoff capacity before acquiring the shared mutation/disclosure fence, then under that fence revalidate binding, current authorization and captured identities/revisions; commit the immutable response to the reserved handoff before releasing the fence. A deletion ordered before handoff prevents disclosure; one ordered after handoff cannot retract bytes already committed for delivery. Do not hold the fence across client-controlled network I/O or queue waits. If no real coordinator and irrevocable bounded handoff exist, do not claim this ordering and block the affected alpha path. Model calls occur outside the fence; an epoch-only or non-atomic recheck is not enough. Deterministically test both deletion/correction orderings and generation changes.
- **Restore and migration:** Keep the companion `visibility-isolated-ingestion.md` deletion-recovery and external-old-binary-fence gates mandatory for legacy migration. A same-user advisory SQLite lock alone cannot fence old binaries or direct file opens; if the operational fence cannot be demonstrated, legacy migration is blocked. Synthetic fresh-store alpha can be tested without legacy migration, subject to its own gates. For recovery, reconcile against an independently durable, authenticated deletion/effect history with a protected freshness watermark outside the restored database and backup domain; otherwise fail closed whenever post-backup effects cannot be proven absent. An operator's approval alone is not evidence that no later deletion occurred. Do not claim immediate physical erasure of old backups or external copies.
- **Acceptance:** Test replacement of artifacts between verification and loading; evidence-free vectors; malformed and nonfinite document output with atomic rollback; wrong-profile stores with same-scope names; direct/unverified vector writes; deleted-record ABA and generation ABA; both sides of the handoff fence; restore after deletion, expired/unavailable deletion history and divergent lineage; and refusal of legacy migration without a proven real old-binary fence. Exercise lexical-only mode through the real entry point and verify its explicit lexical label; unavailable/incomplete hybrid must fail instead of silently changing mode.

## Review round 2: selected contract and remaining gates

The frozen `ab26a2472652be9d5ca167b8e859753cabcb6cbda3d8cbb4c63820ae9e075fb3` received REQUEST_CHANGES from both GPT-6.1 Terra and Claude Sonnet 5.5. Provider/session usage records confirm the actual requested model names and one API call each; full review artifacts are `docs/reviews/vector-design-ab26a247/`. The following selects or tightens the earlier alternatives; it supersedes contrary or ambiguous text above. No mechanism below is implemented or approved merely by being specified.

1. **One authority and mandatory lock order.** Every admitted writer or authority change that can affect record content, source links, evidence, grants, active generation, store lineage, or disclosure—also repair, migration, restore, activation and deletion—must acquire the same independently enforced cross-process mutation/disclosure fence **before** any SQLite write transaction, then hold it through commit or rollback. Acquire in this order: handoff capacity reservation when applicable; external fence; SQLite transaction; release SQLite, then fence; never hold the fence during client-controlled network I/O. No writer, startup process, old binary, utility, background worker or direct SQL path may bypass this protocol while the store serves. If this cannot be enforced, block serving and writes, including fresh stores; a Python lock, SQLite transaction, or trigger alone is not an external fence. Define fenced crash recovery, lock owner death, generation tokens, timeouts and cross-process progress in implementation and review. A diagnostic-only tool is separate, read-only, cannot supply recall results or mutate authoritative state, and must not run concurrently outside the enforced boundary.
2. **Choose gated writes plus per-vector evidence.** No OR branch: every write is routed through the authenticated, fenced verified generation path, and every eligible vector has evidence binding profile/store lineage, scope, record non-reusable incarnation and revision, canonical input, generation activation, and the **exact stored float32 bytes**. Materialize each model output in owned immutable canonical float32 bytes, validate those same bytes, and publish those exact bytes with evidence in one transaction. Do the same for query outputs before use. Verify the actual vec0 bytes/evidence mapping and dimension/finite values on publication and before every eligible vector can contribute to recall; map batches by explicit unique record/input key, not unverified positional assumptions. Missing, duplicate, altered or unverifiable evidence fails closed. Digest algorithm and encoding must be specified and collision-bounded; a digest is not a proof of model correctness. Confirm actual sqlite-vec serialization/readback and native endianness on each supported platform. Validate records and evidence using a single coherent snapshot under the disclosure protocol.
3. **Mutation backstops and binary compatibility.** All admitted writers use the coordinator and verified mutation API. SQLite triggers/constraints on authoritative ordinary tables additionally bump or invalidate record revisions and associated evidence on every supported content/link/correction/delete SQL mutation; vet actual deployed SQLite/vec0 constraints, `REPLACE`, recursive triggers and pragma configuration, and do not assume triggers on vec0 or shadow tables. Direct vec0 writes go through the fenced wrapper; byte-evidence checks independently detect inconsistent rows. Register the complete trigger/DDL manifest for preflight. Test every supported writer with correct and intentionally disabled pragmas; disable serving if unsafe writer paths or extension availability cannot be constrained. This does not protect against hostile privileged same-user SQL outside the declared boundary. Fresh stores as well as migrations require an enforced old-binary/direct-writer fence: test actual old binaries and direct SQLite opens under their real operational identities against a fresh store. If they can silently mutate or bypass the coordinator, mixed-binary use and alpha admission are blocked; a schema version or SQLite exclusive lock is not a fence.
4. **Offline rebuild lifecycle.** Select exclusive offline rebuild, not an online background transition. Fence the store from **all** normal readers, writers and old binaries for the entire rebuild; model computation may run outside a SQLite transaction while that exclusive operational fence remains held. Persist versioned states BUILDING, VALIDATED, ACTIVE, RETIRED, FAILED and exact owner/fence lineage. Each bounded staging write validates profile, active authority, source incarnation/revision, input and output under the writer protocol. Staging generations are never queryable. Activation is one transaction after a full inventory and validation of the current eligible source set, per-row evidence and vec0 bytes; only one generation may become ACTIVE. A crash leaves the store fenced until an explicit operator recovery inspects expected registry, vec0 and shadow-table inventory and decides resume or rollback. Do not auto-delete unknown or orphan objects; explicit authorized cleanup requires a verified backup and known ownership. Rebuild/switch race tests mean attempts by normal readers and writers must be rejected or held outside the fence—not that online generation switching is supported. Activation rollback/commit ambiguity is resolved by inspected durable state, never presumed success.
5. **Query model and artifact lifetime.** Document and query embedders are both constructed exclusively by the trusted factory from the same verified generation's immutable artifact snapshot and compatible, separately specified document/query contracts. A self-reported query contract or model ID is insufficient. Bind query output to the captured non-reused activation and compare the verified query descriptor with the generation in the read snapshot and again under the disclosure fence. Freeze exact adapter/preprocessing code digest and pinned inference, tokenizer and quantization library versions, configuration, platform/device and relevant kernels; absent evidence fails closed. Default rule: any output-affecting implementation/runtime change requires a new generation; a compatible variant needs a separately reviewed deterministic or bounded validation predicate, not a manual version string. The snapshot must stay stable for the full lifetime of each bound process/model, including lazy tokenizer reads, memory mapping and inference; prevent admitted writers from modifying it, verify identity on bind and fail on uncertainty. Stop the affected path if lifetime immutability cannot be enforced.
6. **Binding, rollback and deletion semantics.** A trusted operator provisions a random non-reused instance identity and independent expected profile binding in a protected authority store outside the vector database; the resolver must derive active profile and expected binding through separately verified inputs, not trust the database path or a copied field as independent evidence. A protected, authenticated external monotonic lineage/effect watermark and allocator high-water mark outside the database and its rollback/backup domain must be reconciled on every open and on every mutation/disclosure under the external fence—not merely during an explicit restore ceremony. Missing, stale, divergent, unprovable or rolled-back state blocks service until separately authorized reconciliation; define crash windows and history replay before claiming it works. This is an intentional alpha blocker if no such authority exists. Deletion acknowledgement means the authoritative transaction and disclosure fence have ordered the deletion; previously enqueued responses can still be delivered after acknowledgement, and no maximum end-to-end delivery time is promised. Deleting records and vectors is logical removal from the live DB; SQLite free pages, WAL, vec0 shadow tables, SSD wear, backups and copies may retain bytes. Document and test the selected secure-delete/checkpoint/vacuum and backup-expiry policy without claiming physical erasure beyond what is proven.
7. **Performance cannot weaken correctness.** Full per-eligible-row evidence and vector-byte validation remains the required initial implementation. The per-query scan may be commercially unacceptable; measure it and block scale if necessary. A future incremental authenticated structure or revision/count shortcut may replace it only after a separate soundness proof, corruption/rollback threat analysis, tests and independent review. Periodic sampling or a count alone cannot establish per-row integrity. No diagnostic API is accepted as a retrieval source.
8. **Additional acceptance tests.** Use separate OS processes as well as connections. Test a writer blocked between query revalidation and handoff, both deletion orderings, stalled clients and fence-owner death; mutable/reused model buffers, altered stored vector bytes with unchanged evidence, input/output batch misassociation, NaN/overflow outputs, and rollback after each stage; unverified/wrong query factory; artifact mutation after lazy load; direct SQL mutations and unsafe pragmas; fresh-store old-binary refusal; generation lifecycle crashes and orphan inspection; DB file-level rollback with the same profile ID; authority loss and ABA across restores and cloned instances; and accidental use of diagnostics for recall. Inject process kill at staging, activation and disclosure boundaries; distinguish process crash tests from unproven power-loss guarantees. Review claims about SQLite/vec0 trigger behavior against the deployed versions, rather than accepting a model's recollection.

## Review round 3: publication completeness and recovery ordering

The frozen `f1e35a97b56d8294d7a57b2f8f356d41cf87a9c41d5aecf5fe95c7435e1dde7d` received REQUEST_CHANGES from GPT-6.1 Terra and Claude Sonnet 5.5, with actual model/provider usage verified and full responses saved in `docs/reviews/vector-design-f1e35a97/`. This section supersedes earlier conflicting descriptions. Each protocol is an unimplemented stop gate, not a currently provided guarantee.

1. **Physical and logical set integrity before ranking.** In the same immutable read snapshot, enumerate the active physical vec0 rows and independently derive the complete authorized logical vector-bearing record/evidence set. Verify a collision-free one-to-one correspondence among row key, profile/store, scope, active generation, current record incarnation/revision, canonical input and evidence, with no duplicate, missing, orphan, wrong-scope, ineligible, unverified or extra physical row. An extra hidden or orphan vector must not affect ranking, limits or fallback behavior. If complete set validation cannot be performed without leaking hidden membership or cannot be bounded safely, do not serve the affected path; do not turn a hidden-dependent timeout or count into an externally distinguishable oracle. An alternatively engineered candidate search may rank **only** a fully authenticated, authorized set if an independent review proves exclusion before ranking and limiting; post-filtering alone is not that proof. Add closer-orphan and closer-ineligible cases with positive visible controls, and compare absent vs hidden behavior under scale and time limits. Untrusted-principal claims remain separately blocked.
2. **Versioned eligibility and exclusions.** The eligible set is a deterministic versioned function bound to the generation descriptor, evaluated against authoritative scoped record state within that snapshot. Enumerate supported record types and approved source/input states, limit and extraction outcomes; no caller-provided flag or mutable job can shrink it. Every otherwise relevant record has either matching complete vector evidence or an authenticated generation-bound exclusion with a defined nonsecret reason and source incarnation/revision. Activation requires exact key-set reconciliation, not just counts. Unknown states, malformed extraction or unrecorded exclusions fail closed; corrections and deletion update membership under the fenced authority protocol. Exact schema and reason catalogue remain required implementation deliverables.
3. **External write-ahead effect protocol.** Use a distinct per-store coordinator identity and an independently durable, authenticated, append-only external authority (outside the SQLite backup/rollback domain), under the same store-wide fence. For every admitted mutation with durable externally relevant effects, including deletion and allocation: durably append a uniquely sequenced intent containing the lineage, operation class, nonreused incarnation/effect identifiers and enough protected replay material or commitments for safe reconciliation; commit the matching intent/operation marker and effects in SQLite with verified `synchronous=FULL`; durably append a matching external finalize; only then acknowledge success and release the fence. An external intent is not an acknowledged success. Reconciliation after crash must distinguish intent-only, SQLite committed but not externally finalized, finalized history ahead of SQLite, and database ahead without a matching authorized intent; the last two fence service and never auto-advance. Resolve ambiguous commit by inspecting both independently durable histories, applying an explicitly specified idempotent roll-forward or recorded abort only when safe and authorized; unknowns remain fenced. An old backup is never accepted as current merely because a stale watermark matches it. Define and independently review cross-system crash/restore/failover and external-authority outage behavior before activation. This protocol relies on verified OS/storage durability assumptions; process-kill tests do not prove power-loss durability.
4. **Bypass detection is not authority.** Only externally allocated/reconciled incarnation/revision/activation values and a validated coordinator transaction context may authorize evidence. SQLite triggers on ordinary tables are defense-in-depth invalidators/detectors, not a source of authoritative revisions; an unmatched state, unlogged mutation, missing coordinator proof, altered DDL or inconsistent high-water mark fences the whole store and cannot be laundered into valid evidence by re-embedding. Do not assume a trigger can persist a poison marker after an aborted or rolled-back transaction. Define a verified connection-level proof and database/external reconciliation that detects bypasses before serving; if detection or the enforced distinct-identity boundary fails, block operation rather than rely on a trigger. Test `REPLACE`, trigger-recursion/foreign-key settings and missing extension behavior on the deployed SQLite. Hostile privileged access able to bypass the boundary remains out of scope, but accidental direct open by user processes and known old binaries must be denied or detected—not silently accepted.
5. **Disclosure epochs and bounded failure.** Under a SQLite snapshot capture a store lineage/activation and a nonreused per-scope membership/authorization/evidence/vector mutation epoch advanced transactionally by every admitted operation that can change the candidate set, ranking, grants, source, evidence or vec0 bytes. Capture per-record incarnation/revision as well. Full set and byte validation runs in the snapshot outside the disclosure fence. Under the fence recheck external history, profile/authority, scope epoch and generation, and reauthorize/revalidate final candidates and their immutable bytes before the irrevocable trusted handoff. Every permitted mutator uses the same fence; a changed epoch causes a bounded retry and then a generic unavailable result, not unbounded starvation or stale publication. Specify and measure admission/load, fence wait and lock-hold deadlines and prove other writers/revocations make progress. These limits do not prove timing indistinguishability or guarantee availability.
6. **Handoff and deletion disclosure.** 'Bounded' means bounded reservation capacity and reservation/lock-hold time, not a guaranteed end-to-end delivery deadline. The actual irrevocable point must be a concrete trusted coordinator enqueue committed for delivery to the authenticated intended recipient; bytes committed before deletion may be delivered after deletion acknowledgement, including after a stalled client resumes, and cannot be retracted by the delete. Display this residual in the deletion/recall operator documentation; do not claim delivery cessation at acknowledgement. Queue capacity exhaustion fails without disclosure and cannot block the fence while waiting. If a stricter user-facing deadline is desired, it requires a separate cancelable delivery protocol and cannot be claimed merely by attaching a TTL to an already irrevocable handoff. Test stalled clients, full queue, owner crash and deletion before/after enqueue.
7. **Operational fence and rebuild ownership.** The intended strong fence is an authenticated local coordinator/store-owning service under a distinct OS identity or equivalent independently enforced sandbox, with SQLite DB, WAL/SHM, vectors, authority files and containing directories inaccessible to other ordinary user processes and old binaries except through its checked API. Test the actual target OS, operational identities and direct-open attempts. If that class is unavailable, fresh vector alpha and legacy migration remain blocked; do not relabel advisory locks as enforcement. The trusted operator provisions and pins the intended profile/instance through an independent authenticated client binding; compare it to the profile resolver and independent authority before every operation. Ambient selection alone is not proof of caller intent. Maintenance owns an exclusive **store-wide** fence with a unique non-reusable owner lineage/token; staging operations validate that ownership, not recursively reacquire a non-reentrant fence or allow another process to join. Normal readers, writers and deletion wait only to a bounded deadline or receive unavailable; no delete is acknowledged while deferred. A preemption/checkpoint/resume mechanism is optional and disabled until designed and tested; recovery after owner crash is fenced and explicit. State clearly that lengthy rebuilds reduce availability.
8. **Legacy disposition and runtime fingerprint.** Split schema migration (short validated SQLite transaction, no model computation) from exclusive staged rebuild. Inventory recognized legacy vector/FTS/shadow objects against an exact manifest; unknown objects block. Preserve recognized legacy vectors as explicitly `LEGACY_QUARANTINED`, non-queryable, non-writable, and reserved against name reuse; removal requires explicit operator authorization, protected verified backup and deletion/retention policy. Old vectors in quarantine, WAL and backups can retain sensitive information. Descriptor v1 supports canonical little-endian IEEE 754 float32 only; other formats or platform readback incompatibilities block activation. Hash an unambiguous domain-separated, length-prefixed byte framing containing version, store/generation/record keys and exact stored vector bytes; specify numeric widths, encoding and digest algorithm in reviewed DDL/codec before implementation. Pin a closed manifest of adapter and preprocessing code digests, model/tokenizer/config files, libraries, quantization/kernels, device and relevant runtime versions. Unclassified output-affecting inputs or incompatible runtime/platform cause explicit rebuild-required failure; a compatible variant is disabled until an independently reviewed model-specific measured predicate exists. No silent lexical fallback.

## Review round 4: explicit integrity and recovery semantics

The frozen `535ca817651442eae6fab069b453dbe6603ff7a262a981520b7dab71b5c424f6` received APPROVE from GPT-6.1 Terra and REQUEST_CHANGES from Claude Sonnet 5.5; their verified model/provider records and full outputs are `docs/reviews/vector-design-535ca817/`. This section supersedes conflicting earlier language. Every mechanism here is an unimplemented prerequisite, not a deployment claim. In particular, full codec, capability provisioning, external history durability, recovery and authority protocols require concrete schemas, verification and independent review before operation.

1. **Separate integrity from visibility.** The integrity inventory is caller-independent and covers every physical vector and evidence row belonging to a scope/generation, including non-active artifacts according to their explicit state. An extra, missing, orphan, duplicate, wrong-scope or mismatched row is an integrity violation: fence the affected store and return generic unavailable; give only a privileged operator diagnostic with no record IDs. This is an availability signal and is not a hidden-record noninterference guarantee. In this initial trusted single-user alpha, a scope/generation admitted to hybrid recall must have one uniform visibility class for its authorized principal. If the active content-dependent policy makes any member differently visible to that principal, block hybrid recall for that scope rather than rank mixed-visibility vectors or expose withheld IDs. An explicitly requested lexical mode remains separate. The untrusted-principal and mixed-visibility cases are not admitted by this design. Tests require a visible positive control without corruption and generic unavailable on an orphan or mixed visibility, not unchanged success; no timing/confidentiality claim follows.
2. **Validate before intent; abort deterministic rejects.** Acquire capacity reservation when applicable and the exclusive store-wide fence. Resolve the principal and current authenticated policy, then validate existing state, record incarnations/revisions, generation, intended operation and inputs before creating an intent. Allocate externally backed non-reused identifiers and durably append the intent only for a well-formed, authorized proposed operation. Begin `IMMEDIATE`, repeat all authority/state/ABA checks and either commit the matching operation marker/effects with verified durability or roll back. A live coordinator that still owns the validated fence may durably append a coordinator-authenticated ABORT for a deterministic pre-commit rejection or confirmed rollback, with no user-level approval; it must never acknowledge the mutation as committed. If intent append, abort, commit outcome, fence ownership, or post-commit finalization is uncertain, fence the store and reconcile, not auto-abort. Crash-orphaned intents require the audited recovery ceremony. Verify authorization and that no sensitive unvalidated effect is included in intent; test every crash point and ordinary concurrent rejection without spurious permanent fencing.
3. **Operation catalogue and genesis.** Every authoritative change to source/content, record links, correction, deletion, grants, exclusion, vector bytes/evidence, eligibility or scope epoch, generation state/activation, identity allocation, schema migration, enrollment and restore requires an externally authenticated intent and finalize or recorded abort, with the external allocator covering all non-reused identities/revisions and epoch advances. No durable mutation is exempt merely because it is called maintenance. Bootstrap fresh store and legacy enrollment via a separately specified, bounded bulk GENESIS operation under the same exclusive fence: establish independent intended-profile binding, vetted immutable input inventory, ledger lineage and high-water, allocate non-reused incarnations/revisions, then transactionally write DB identity and genesis marker before external finalize. A legacy genesis treats operator-approved pre-migration bytes as the input baseline; it cannot prove prior deletions or restore missing historical authority. If history, provenance, schema or old-binary fence cannot be proven according to the migration gate, legacy enrollment stays blocked. GENESIS intent content, size limits, chunking, crash recovery and commit/marker linkage are implementation and review gates, not facts established by this document.
4. **Restore and bypass reconciliation.** Enter `RESTORE_RECONCILE` fenced; verify the backup's authenticated lineage, exact consistency point and the complete externally authenticated suffix and current high-water from an authority outside its rollback domain. Under the external write-ahead protocol, replay supported idempotent effects by non-reused incarnation, including deletions and grant revocations; invalidate evidence and rebuild any affected generation rather than treating old vectors as current; advance allocators beyond all committed or reserved identities without reuse. Verify resulting authoritative state and sequence, then finalize a new restore-lineage record before opening service. A bypass-fenced store cannot be laundered by a normal revision: reconcile from authenticated history, invalidate affected evidence and require an explicitly authorized rebuild. If the suffix, authorization, effect payload, state integrity or freshness cannot be proven, there is no automatic or operator-override exit to the old lineage. A separate new-lineage import is possible only from independently authoritative sources after the deletion/recovery policy proves what may be imported; otherwise remain blocked. Rebuilding does not itself prove a previously deleted item is safe to reintroduce.
5. **Generation lifecycle and retention.** Permitted state transitions are BUILDING→VALIDATED→ACTIVE→RETIRED, or BUILDING/VALIDATED→FAILED; no RETIRED or FAILED generation can become ACTIVE again. A new attempt uses a fresh non-reused activation/lineage. At most one ACTIVE generation per scope; staging and non-active generations are never queried and retain reserved, collision-checked physical names. Deletion commits atomically invalidate or remove affected vectors/evidence in every accessible live generation under the same fence; if an inaccessible retained generation cannot be scrubbed, deletion must report that residual under explicit retention policy and it cannot silently become active. RETIRED, FAILED, legacy-quarantined tables, WAL, free pages and backups can retain sensitive information and are not claimed physically erased. Cleanup is explicitly authorized after verified backup and inventory; unknown objects block. Offline rebuild availability and no-acknowledged-deletion while maintenance holds the fence remain as specified above.
6. **Authority tables, grant source and detection.** The authorized alpha principal and scope grants are authoritative in the store DB and all changes are mediated through the fenced coordinator and external operation history. A separate external revocation source is outside the ordering claim unless it is integrated into the same serialization; otherwise that feature is disabled. The exact DDL/trigger/connection and external-history consistency manifest covers all authority-bearing tables: records, links, grants, scope membership/epochs, registry and activation, exclusions, vector evidence, operation markers and allocation/lineage state; the vec0 wrapper and byte checks cover virtual and shadow data. On open and under the fence at each disclosure compare DB-authoritative state and transaction markers to the independently retained external-history-derived expectation; unexplained change blocks service. Test unauthorized direct SQL on each class and verify that incomplete detection cannot be promoted as a guarantee. Triggers that can be disabled or cannot persist a poison marker are not sole evidence.
7. **Outcome and fence timing.** Use one exclusive store-wide mutation/disclosure fence in this alpha, including grants and maintenance; shared modes are not assumed. Reserve bounded outbound capacity before acquiring it. For each retry, release the prior reservation before retrying and obtain another only within a fixed deadline; timeout gives generic unavailable without handoff. After SQLite commit and external finalize, write the immutable local outcome or response to the reserved trusted handoff under the fence; that irrevocable enqueue is the acknowledgment/disclosure linearization point. Release the fence before network or client-controlled delivery. A successfully enqueued outcome can be delivered after a later deletion; a process crash may leave a committed effect whose response was not delivered, so callers must query a separately authenticated operation outcome rather than assume failure or success. Bound enqueue/fence hold and verify progress under saturation; no finite end-to-end delivery deadline or constant-time claim is made.
8. **Evidence and client capabilities.** The full versioned, length-delimited, domain-separated evidence frame covers store/profile identity and lineage, scope, record key, non-reused incarnation and revision, canonical input digest, generation activation and descriptor digest, format/dimensions, and exact canonical vector bytes; exclusion evidence covers the same applicable identity/lineage/input fields and a bounded reason. Its authenticator is a coordinator-only keyed MAC or equivalently independently authenticated external-history commitment under the fenced authority; an unkeyed digest alone is not authorization. Exact algorithms, widths, canonical encoding, key lifecycle, rotation, scope and platform readback are implementation gates. A per-profile client capability issued by the distinct-identity coordinator during explicit operator provisioning binds intended profile/instance independently of environment and resolver; protect it from other ordinary profiles/processes via the actual OS boundary, scope and revoke it, and never log it. Same-user hostile compromise remains outside the stated boundary, but common environment/configuration mistakes must fail. Test mismatched environments and same-named scopes, field swaps, omitted fields, clone/capability revocation, unauthorized table writes, allocator replay, valid vs invalid live abort, and crashes before/after each intent/commit/finalize/handoff transition.

## Acceptance tests and stop conditions

- Same claimed model ID with different weights, tokenizer, adapter runtime, query prefix, dimension, metric, paragraph/fence version or centroid/head configuration: refuse mixed state; unchanged contract survives restart. Test intentional asymmetric query/document compatibility and unknown custom adapters.
- Force truncated-name collisions, registry/table mismatch, unregistered legacy vectors, invalid metadata, malformed descriptors, missing tables and finite but stale vectors. Refuse without mutation. Do not conflate an empty or absent store with an initialized generation.
- Through actual production entry points and two independent connections, race embedding with delete/correction/rebuild and race query with generation swap; assert no stale publication and no mixed-snapshot result. Include visible controls and restricted-content tests. Cover direct vector writes and all source mutations.
- Inject SQLite `ABORT` and `ROLLBACK`, extension DDL/DML errors and commit ambiguity; verify records, FTS, vectors, evidence, registry, jobs, audit and version from a fresh connection. Validate actual deployed sqlite-vec semantics, not only mocks.
- Back up and rebuild representative legacy fixtures with exact preflight; test unsupported schemas and old-binary attempts before any mutation. Confirm deletion recovery and profile isolation separately. Run a real-model end-to-end case and `scripts/test.sh` after focused regressions.
- Measure runtime/memory of integrity validation as corpus size grows; do not assume an exhaustive per-query Python scan is commercially viable. Correctness is not waived for speed.

**Gate:** no claim of safe legacy vector use, per-profile alpha admission, or commercial release until implementation is frozen, regression-tested, independently adversarially reviewed on a later turn, and the operator approves the phase transition. The previous review and currently passing tests do not approve this proposed design or current uncommitted changes.
